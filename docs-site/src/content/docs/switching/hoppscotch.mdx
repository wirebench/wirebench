---

Hoppscotch exports collections and environments as separate JSON files. Wirebench reads both, at
every schema version Hoppscotch has written: each collection, folder and request is read at its
own version, so a file that mixes old and new objects imports whole. Each top-level collection
becomes a **REST API** in the project you choose; its GraphQL requests come along as requests with
a GraphQL body.

Collection and folder variables become project properties. Environments become workspace
environments. Scripts are attached to their requests, folders and API, switched off, and run once you
read and switch them on. Credentials do not come across as plain
text. The import summary lists everything that was left out or changed.

## Steps

<Steps>

1. Open **Import…**; it detects the format, or pick **Hoppscotch collection** or **Hoppscotch
   environments** yourself.

2. On the **File** tab, pick or drop the exported `.json` file. Or paste its text on the **Paste**
   tab. There is no URL tab.

3. For a collection, choose the target project. An environments file lands in the workspace, so the
   dialog does not ask.

4. Choose **Import**, then read the summary.

</Steps>

## What carries over

### Collections

| In the export | In Wirebench | More |
| --- | --- | --- |
| A top-level collection | A REST API with its name. A file of several collections gives each its own | |
| A folder | A folder in the API, in the export's order | |
| Collection and folder headers | Copied onto each request below that does not set the same header, and a note says so | |
| Collection and folder auth | The auth of the API and the folder. A request with auth **inherit** takes it | [Auth](/wirebench/docs/guides/auth/) |
| Collection and folder variables | Project properties, outermost first. A secret variable becomes a secret with no value, listed so you can set it | [Environments and properties](/wirebench/docs/guides/environments/) |
| `<<name>>` | `${name}` | [Property syntax](/wirebench/docs/reference/property-syntax/) |
| `<<$guid>>` and the other predefined variables | The matching dynamic variable, where Wirebench has one | [Dynamic values](/wirebench/docs/reference/property-syntax/#dynamic-values) |

### REST requests

| In the request | In Wirebench | More |
| --- | --- | --- |
| Method and endpoint | The request's method and URL. The endpoint's own query string becomes **Params** rows | [REST](/wirebench/docs/guides/rest-client/) |
| Parameters | Rows in the **Params** table, an inactive one switched off. A name the endpoint's query already has is not added twice | |
| Headers | Rows in the **Headers** table, with their descriptions | |
| A JSON, XML, HTML or text body | A raw body. When no `Content-Type` header is set, one is added from the body's type | [Request body](/wirebench/docs/guides/rest-client/#request-body) |
| A URL-encoded body | A form body, one field per `key: value` line; a line starting with `#` is switched off | |
| A multipart body | A multipart body. A file part has no file in the export, so it is kept as a switched-off text part, with a note | |
| A file body | Left out, with a note: the file is not in the export | |
| Saved responses | [Response examples](/wirebench/docs/guides/rest-client/#examples), masked as every import masks a recorded response | |
| The description | The request's description | |
| Scripts | See [Scripts](#scripts) | |

### GraphQL requests

A GraphQL request becomes a `POST` request with a [GraphQL body](/wirebench/docs/guides/graphql/):
its query and its variables. Its headers and auth come across as for a REST request.

### Auth

| In the export | In Wirebench |
| --- | --- |
| None, inherit | The same |
| Basic, Digest | The same type, with the user name |
| Bearer | Bearer |
| API key in a header or the query | API key, with its name and placement |
| OAuth 2 | OAuth 2 with the authorization code, client credentials or password grant, its URLs, client ID and scopes. Extra request parameters are noted |
| AWS Signature | AWS Signature v4, with the region and service |
| JWT | JWT, with the algorithm, claims and where the token goes |
| Hawk, Akamai EdgeGrid | Auth **none**, with a warning |
| Auth switched off | Auth **none** |

### Environments

- **Each environment** becomes a workspace environment, renamed when the name is taken and **never
  made active**.
- **The global environment** (named `Global`) merges into Globals instead.
- **Values.** A variable's current value, else its initial value. Current exports leave every
  current value empty, so the initial value is what usually arrives.
- **Secret variables** never carry a value in an export. Each becomes a secret with no value,
  listed in the summary so you can set it.

A variable whose name looks like a credential and whose value is a literal becomes a secret, with a
note.

### Scripts

Every pre-request and test script is attached where it was: a collection's to the API, a folder's to
the folder, a request's to the request. A request's test script becomes its post-response script.
The scripts are **switched off**, so they run once you read them and switch them on, against the
`pw`, `hopp` and `pm` names Hoppscotch gives them. The summary lists, per request, the calls Wirebench
cannot run. See [Scripts from other clients](/wirebench/docs/guides/scripts/#hoppscotch-scripts)
for what is supported.

## Credentials

No literal credential is written into a project or workspace file. Passwords, tokens, API key
values and client secrets are not copied, and the summary counts the auth configurations that need
one. Enter each on its **Auth** tab; Wirebench stores it encrypted outside the project.

## What does not carry over

| In the export | What happens | What to do |
| --- | --- | --- |
| Request variables | Not imported, with a warning: Wirebench has no request-level property scope | Add them as project properties, or set them from a script |
| A version newer than this build knows | Read as the newest one, with a note naming it | |
| An environments file picked as **Hoppscotch collection**, or the other way round | Refused, with a message saying which to pick | |
| WebSocket, SSE, Socket.IO and MQTT requests | Hoppscotch does not export them | |

## The command line

`wirebench import <file>` reads a Hoppscotch collections export and adds its APIs and its plain
collection and folder variables as project properties, and attaches the scripts switched off as the
desktop does: switch them on by deleting the `enabled: false` line under `scripts:` in the `.yaml`
file of the request, folder or API. It has no secret store or workspace, so it lists secret variables
as not imported. An environments file is refused.

## Limits

- A file larger than 50 MB is refused, picked or pasted.
- Folders nested more than 64 levels deep are cut at that depth, with a warning.

## After importing

<Steps>

1. Read the summary, or choose **Copy report** to keep it as a checklist.

2. Enter the passwords, tokens and keys it counts, on each **Auth** tab, and the values of the
   secrets it lists. See [Secrets](/wirebench/docs/guides/secrets/).

3. Pick one of the imported environments to make it active. Import never switches environments for
   you. See [Environments and properties](/wirebench/docs/guides/environments/).

</Steps>

<Aside type="note" title="Scripts are off until you switch them on">
An imported script is code nobody on your team has read yet. Read it, then switch it on. A call
Wirebench cannot run, such as `hopp.fetch` or a top-level `import`, fails with `script-unsupported`.
</Aside>
