A Postman collection becomes **one REST API** in the project you choose:
- folders become folders;
- requests become requests;
- `{{variables}}` become Wirebench properties.

Collection variables come across as project properties, and environment and globals exports have
their own import. Credentials do not come across. Pre-request and test scripts do, switched off
until someone has read them. The import summary lists each of these, so you know what to set up before
the first send.

To run the import, see [Postman collections](/wirebench/docs/guides/importers/#postman-collections) in
the importers guide. It takes Collection v2.0 and v2.1 JSON, from a file or pasted, and Collection v3
folders — see [Collection v3 folders](#collection-v3-folders) below.

![The import summary for a Postman collection: three requests in one folder, and five things to look at, from scripts to credentials](/wirebench/docs/images/switching/postman-summary.png)

## What carries over

| In Postman | In Wirebench | More |
| --- | --- | --- |
| The collection, its name and description | A REST API with the same name and description | [REST](/wirebench/docs/guides/rest-client/) |
| A `baseUrl` or `base_url` collection variable. Without one, the origin of the first full URL | The API's **Base URL**, also offered as a suggestion in that field. Request URLs that started with `{{baseUrl}}` become relative paths | [REST](/wirebench/docs/guides/rest-client/#create-an-api-and-a-request) |
| Folders, nested, with their descriptions | Folders, nested the same way | |
| Requests: method, URL and description | Requests. A request saved as a bare URL string is a GET | |
| `{{name}}` anywhere in a name, URL, header, query, body or auth field | `${name}`. It looks the name up in the active environment first, then the project, the workspace and global properties | [Property syntax](/wirebench/docs/reference/property-syntax/) |
| Collection and folder variables, other than the base URL | Project properties. A secret-typed variable becomes a secret in the secret store. A name the project already has keeps its value; the summary lists it | [Environments and properties](/wirebench/docs/guides/environments/) |
| Environment and globals exports | **Import…** → Postman environment / Postman globals. An environment becomes a workspace environment (renamed when the name is taken, never made active); globals merge into Globals; secret-typed values go to the secret store | [Importers](/wirebench/docs/guides/importers/#postman-environments-and-globals) |
| `:id` path segments and their values | `{id}` in the URL, with a row in the **Path parameters** table | [Path and query parameters](/wirebench/docs/guides/rest-client/#path-and-query-parameters) |
| Query parameters and headers, including disabled ones | Rows in the **Params** and **Headers** tables. Disabled rows stay off | |
| A raw body (JSON, XML, text…) | A raw body in the same language | [Request body](/wirebench/docs/guides/rest-client/#request-body) |
| An `x-www-form-urlencoded` body | A form body | |
| A `form-data` body | A multipart body. File fields keep the file path | |
| A binary file body | A binary body pointing at the same path | |
| A GraphQL body | A [GraphQL body](/wirebench/docs/guides/graphql/) with the same query and variables. An export writes it back as a GraphQL body | |
| Saved responses | Request examples, with credential headers and values masked and cookies dropped; a body past 256 KB is cut | [Examples](/wirebench/docs/guides/rest-client/) |
| `followRedirects` and `maxRedirects` request settings | The request's redirect settings | |

### Authentication

Auth set on the collection becomes the API's auth. Auth on a folder becomes the folder's, and auth
on a request becomes the request's. A request or folder set to inherit still inherits.

| Postman auth | Wirebench auth |
| --- | --- |
| No auth | None |
| Inherit auth from parent | Inherit |
| Basic | Basic, with the username |
| Bearer token | Bearer. The token is not copied |
| API key | API key, with its name and whether it goes in a header or the query. The key is not copied |
| OAuth 2.0, authorization code (with or without PKCE) | OAuth 2, authorization code with PKCE on: token URL, authorization URL, client ID and scopes |
| OAuth 2.0, client credentials | OAuth 2, client credentials: token URL, client ID and scopes |
| OAuth 2.0, password credentials | OAuth 2, password: token URL, client ID, username and scopes. The password is not imported |
| NTLM | NTLM, with the username, domain and workstation |
| Digest | Digest, with the username. The password is not imported |
| AWS Signature | AWS Signature v4, with the region and service. The keys and session token are not imported |
| JWT Bearer | JWT, with the algorithm, payload, extra header and where the token goes. The secret or private key is not imported; an algorithm Wirebench cannot sign with sets auth to none, named in the summary |

See [Authentication](/wirebench/docs/guides/auth/) for each scheme's fields.

## What does not carry over

| In Postman | What happens | What to do |
| --- | --- | --- |
| Passwords, tokens, API key values, client secrets | Never copied. The summary counts the auth configurations that need one | Enter each on its **Auth** tab. Wirebench stores it encrypted outside the project |
| Dynamic variables such as `{{$guid}}` or `{{$timestamp}}` | Kept as written, and nothing generates a value. One warning in the summary names them all | Replace each with a property, or with a value a script sets |
| Pre-request and test scripts | Imported where they were: the collection's on the API, each folder's on its folder, each request's on the request ([scripts](/wirebench/docs/guides/scripts/#scripts-on-apis-interfaces-and-folders)), run in the same order through a `pm` layer. **Switched off** until switched on. The summary counts them and names the scripts that call something the layer does not support | Read them, then **Switch on** (on a request, the API tab or a folder's **Scripts…**) or **Switch on scripts…** (for an API or folder and everything in it). `setNextRequest` and `skipRequest` steer an API or folder run ([steer a run](/wirebench/docs/guides/scripts/#steer-a-run)). Rewrite a call the layer does not support, such as `pm.sendRequest`; a value one request passes to another can also be a [sequence](/wirebench/docs/guides/sequences/) transfer. To move them off the `pm` layer, [convert them to Wirebench scripts](/wirebench/docs/guides/scripts/#convert-to-wirebench-scripts) |
| OAuth 2.0 implicit grant | Auth set to none. The summary names the grant | Pick a supported grant on the **Auth** tab, or set the token as Bearer |
| Other auth types (Hawk, OAuth 1.0, Akamai…) | Auth set to none. The summary names the type | Set the request's auth by hand, or send the header yourself |
| Items that are neither a folder nor a request | Skipped. The summary counts them | Nothing: there was no request to import |
| A saved response without a status code | Skipped. The summary counts them | Nothing |
| Collections by URL | Not supported | Download the file, or paste its JSON |

<Aside type="note" title="Credentials typed as headers">
A token written straight into a header never reaches the project files. A literal
`Authorization: Bearer …` or `Basic …` header becomes the request's bearer or basic auth, with the
user name only, and is dropped; any other credential-looking header with a literal value, such as
`X-Api-Key` or `Cookie`, is dropped. The summary names each one: enter the value on the **Auth** tab,
where it is stored as a secret. A header made only of variables, such as `Bearer {{token}}`, is kept.
</Aside>

## Collection v3 folders

The v3 format keeps a collection as a folder of YAML files, one per request, usually under
`postman/collections/` in a git repository. Pick it in **Import…** with **Folder…**, or pick its
`.resources/definition.yaml` with **Browse…**; `wirebench import <folder>` takes the same paths. A
workspace folder — one holding `collections/`, `environments/` and `globals/` — imports every
collection in it, with its environments (never made active) and globals.

Everything in the tables above applies: an HTTP request carries over exactly as a v2.1 request does.
What differs:

| In a v3 folder | In Wirebench |
| --- | --- |
| A folder's or the collection's `.resources/definition.yaml`: name, description, variables, auth, scripts | The folder's or API's, as above |
| `order` on requests and folders | Their order in the explorer; a request without one comes last |
| `*.example.yaml` under `.resources/<request>.resources/examples/` | Request examples |
| gRPC requests: method path, metadata, message | A separate gRPC API named `<collection> (gRPC)`. It needs a definition: import the `.proto` or use server reflection |
| WebSocket requests: URL, query, headers, handshake timeout, saved messages | A separate WebSocket API named `<collection> (WebSocket)` |
| A script whose source is in a file the entry names | The script, read from that file when it lies inside the collection |
| GraphQL, Socket.IO, MQTT, MCP and LLM requests | Not imported. The summary names each file |
| Fields Wirebench does not read, such as `settings.strictSSL: false` or a field the format does not document | Left out. The summary names them per file |
| Several auths on one definition | The first; the summary names the others |
| A request file picked on its own | Refused: pick its collection folder |

`wirebench import` has no secret store or workspace: it adds the APIs and the plain variables, and
lists secret variables, environments and globals as not imported.

## After importing

<Steps>

1. Read the summary, or choose **Copy report** to keep it as a checklist.

2. Enter the passwords, tokens and keys it counts, on each **Auth** tab. See
   [Secrets](/wirebench/docs/guides/secrets/).

3. Import the collection's environments and globals with **Import…** → **Postman environment** or
   **Postman globals**. Then only the names the summary still lists need defining, as properties or
   environment variables. See
   [Environments and properties](/wirebench/docs/guides/environments/).

4. Check the API's **Base URL**, then send one request to confirm the setup.

</Steps>
