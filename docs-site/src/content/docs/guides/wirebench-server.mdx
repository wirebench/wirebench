Wirebench Server gives a team sign-in, teams, shared workspaces and live updates, on a machine you
run. This page is for the person who runs it. For using a server from the app, see
[Shared workspaces](/wirebench/docs/guides/shared-workspaces/#sign-in-to-a-server).

## What it gives a team

- **Sign-in.** Accounts are invite-only. People sign in with an email and password, with the team's
  OpenID Connect identity provider, or both.
- **Teams and roles.** A team owns workspaces. Each member has a role in each workspace: *viewer*,
  *editor* or *admin*.
- **Shared workspaces over HTTP.** A workspace shared on the server syncs with the same Sync control as
  a git share, but nobody needs git on their machine. The server stores each push as git commits.
- **Live updates.** The app hears about a teammate's push, a role change or an ended session within
  seconds, and sees who else has a workspace open.
- **Team secrets.** A workspace's admins can share the secret values behind its references, encrypted
  for each approved machine. See [Team secrets](/wirebench/docs/guides/shared-workspaces/#team-secrets).
- **Catch URLs.** A workspace's editors create public addresses that record every webhook sent to them.
  See [Webhook inbox](/wirebench/docs/guides/webhooks/).
- **A browser tab.** Optionally, the server serves the app itself at its public URL, so a teammate opens a
  team workspace without installing anything. See [Browser client](/wirebench/docs/guides/server-browser-client/).

Nothing in the app needs a server. Without one, the status bar shows no account.

## What it needs

- **One process,** by default. Several instances against one database need an Enterprise license and a
  few more things: see [Running several instances](#running-several-instances).
- **PostgreSQL.** The connection string goes in `WIREBENCH_SERVER_DATABASE_URL`.
- **A data directory.** It holds the workspaces' repositories and temporary files: `/data` by default.
  The server checks at start-up that it can write there.
- **git.** The server calls the system `git`. The container image includes it.
- **TLS in front.** The public URL must be `https://`. Put the server behind a reverse proxy that ends
  TLS and forwards `/api/v1/`, `/hooks/` and the WebSocket upgrade for `/api/v1/live`.

## Run the published image

Each release publishes the server as `ghcr.io/wirebench/wirebench-server`, for `linux/amd64` and
`linux/arm64`. The image listens on port `8080`, runs `serve` by default and keeps its data in the
`/data` volume.

<Steps>

1. Create a PostgreSQL database and a user for the server.
2. Run the image with the two required variables, a volume for `/data` and the port:

   ```sh
   docker run -d --name wirebench-server \
     -e WIREBENCH_SERVER_DATABASE_URL=postgres://wirebench:…@db.example.com:5432/wirebench \
     -e WIREBENCH_SERVER_PUBLIC_URL=https://wirebench.example.com \
     -v wirebench-data:/data \
     -p 127.0.0.1:8080:8080 \
     ghcr.io/wirebench/wirebench-server
   ```

3. Point your reverse proxy at port `8080` (see [Behind a reverse proxy](#behind-a-reverse-proxy)).
4. Create the first admin (see [The first admin](#the-first-admin)).

</Steps>

The server applies any pending database migrations when it starts. Its `config check` command lists
each variable as set, defaulted or missing, and never prints a value. `/healthz` reports pass or
fail for the database, the data directory and git, and the image's health check calls it.

## Try it with the compose file

The repository has a compose file that builds the server image from a checkout and runs it beside
PostgreSQL 16, each with a named volume. It is for trying the server on your own machine: the public
URL is `http://localhost:8080`, with `WIREBENCH_SERVER_ALLOW_INSECURE_PUBLIC_URL` on.

```sh
docker compose -f packages/server/compose.yaml up
```

Both ports are published on `127.0.0.1` only: the server on `WIREBENCH_HTTP_PORT` (default `8080`) and the
database on `WIREBENCH_DB_PORT` (default `5432`). Set either when the default is taken.

For a team, the `docker-compose.yml` at the root of the repository runs the published image instead.
[Run your team's API workbench behind your firewall](/wirebench/docs/getting-started/team-server/) walks
through it.

Some variables travel together:

- An `http://` public URL is refused unless `WIREBENCH_SERVER_ALLOW_INSECURE_PUBLIC_URL` is `true`.
- `WIREBENCH_SERVER_OIDC_ISSUER` needs the client id and the client secret, and must be `https://` under
  the same rule.
- At least one sign-in method must be on: local accounts, OIDC, SAML, or any mix of them.

## The first admin

Accounts are invite-only, and a fresh server has none. Create the first server admin from the console,
with the server's `admin invite` command. In the image, the command is `node /app/dist/bin.js`.

<Steps>

1. Run `admin invite` with your email, in the running container:

   ```sh
   docker exec wirebench-server node /app/dist/bin.js admin invite you@example.com
   ```

   With the compose file, `docker compose -f packages/server/compose.yaml run --rm server admin invite you@example.com`
   does the same.

2. It prints a one-time link, `<public URL>/invite/<code>`, valid for `WIREBENCH_SERVER_INVITATION_DAYS`
   (7 days by default).
3. Open the link, or paste the code into the app's **Account: Sign in to a server…** dialog under
   **Have an invitation code?**, and choose a password. You are the first server admin.

</Steps>

An invitation from the console makes a server admin unless you add `--no-admin`. Later invitations come
from the console the same way, or from the app by a server admin. The server sends no email: copy the link and
send it however your team already talks. `admin list-invitations` and
`admin revoke-invitation <id>` help an operator who cannot sign in yet.

## Sign-in

- **Local accounts** (email and password) are on unless `WIREBENCH_SERVER_LOCAL_AUTH` is `false`.
- **OpenID Connect** is on once `WIREBENCH_SERVER_OIDC_ISSUER` is set. Register the redirect URI that
  `config check` prints, `<public URL>/api/v1/auth/oidc/callback`, at the identity
  provider. With the browser client on, also register `<public URL>/api/v1/auth/oidc/browser-callback`,
  which `config check` prints too. A login is linked to an existing account or an open invitation by the
  provider's verified email. It never creates an account on its own.
- **SAML** is on once `WIREBENCH_SERVER_SAML_IDP_METADATA` is set, on an Enterprise server. SCIM
  provisioning comes with it. With the browser client on, the IdP also needs a second ACS URL,
  `<public URL>/api/v1/auth/saml/browser-acs`. See
  [SAML sign-in and SCIM provisioning](/wirebench/docs/guides/server-saml-scim/).
- Sign-in and invitation endpoints accept ten attempts a minute per address and per email. The counters
  live in the process, so a restart resets them.
- Each installation of the app holds a device token. It expires after `WIREBENCH_SERVER_TOKEN_IDLE_DAYS`
  without use, or `WIREBENCH_SERVER_TOKEN_MAX_DAYS` at most. Users see and revoke their devices in the
  app, and disabling a user revokes all of theirs.

## Teams and workspaces

A server admin creates teams, with **New team…** in the app's **Account: Manage teams…** dialog, and
becomes the first admin of each. Team admins do the rest:

- Add people who already have an account, invite new ones, and change or remove roles. A team keeps at
  least one admin.
- Any member can create a workspace in the team and is its admin. Each workspace has a default role for
  the team's members — *none*, *viewer* or *editor*, *viewer* for a new one — and a workspace admin can
  grant any member a different role.

| Role   | Open and pull | Send requests | Push | Manage access | Delete |
| ------ | ------------- | ------------- | ---- | ------------- | ------ |
| viewer | yes           | yes           | no   | no            | no     |
| editor | yes           | yes           | yes  | no            | no     |
| admin  | yes           | yes           | yes  | yes           | yes    |

Team admins and server admins are admins of every workspace of their teams. To anyone without a role, a
workspace does not exist. Deleting a workspace moves its repository under `<data dir>/tmp/`; nothing is
deleted from disk.

## Behind a reverse proxy

Set `WIREBENCH_SERVER_PUBLIC_URL` to the `https://` origin people reach, and
`WIREBENCH_SERVER_TRUST_PROXY` to `true` so the server honours `X-Forwarded-*` headers. The proxy must
forward:

- `/api/v1/` — the API the app talks to.
- `/api/v1/live` with the `Upgrade` and `Connection` headers. Live updates are a WebSocket there.
  Without them, the app shows *Reconnecting…* and falls back to polling; sync keeps working.
- `/hooks/` with every method, the request body and the client's address, when catch URLs are on.
- `/scim/v2/` with every method, when an identity provider provisions accounts over SCIM.
- The whole origin, and `/api/v1/host` with the `Upgrade` and `Connection` headers, when the
  [browser client](/wirebench/docs/guides/server-browser-client/#behind-a-reverse-proxy) is on.

With nginx:

```nginx
location /api/v1/ {
    proxy_pass http://127.0.0.1:8080;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}

location /api/v1/live {
    proxy_pass http://127.0.0.1:8080;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_set_header Host $host;
}

location /scim/v2/ {
    proxy_pass http://127.0.0.1:8080;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}

location /hooks/ {
    proxy_pass http://127.0.0.1:8080;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    client_max_body_size 32m;
}
```

The server pings every live socket every 30 seconds, which keeps an idle connection inside a proxy's
read timeout. A WebSocket upgrade whose `Origin` is not the public URL is refused.

## Limits

- `WIREBENCH_SERVER_BODY_LIMIT_MB` (32 MiB by default) bounds a push and a download. Raise it for
  workspaces with large attachments. Each file is at most 8 MiB.
- Catch URLs keep the newest 500 captures each for 7 days, store up to 1 MiB of each body, and accept 10
  requests a second with bursts of 50. The `WIREBENCH_SERVER_HOOKS_*` variables change these.
  `WIREBENCH_SERVER_HOOKS_ENABLED=false` turns catch URLs off, and the app hides its **Webhook inbox** node.
- A catch URL can check webhook signatures only when `WIREBENCH_SERVER_HOOKS_SECRET_KEY` is set. See
  [Webhook signatures](/wirebench/docs/guides/webhook-signatures/).

<Aside type="caution">
Run one instance per data directory unless every instance is set up as in
[Running several instances](#running-several-instances). An instance left at the default
`WIREBENCH_SERVER_INSTANCES=single` deletes every host lease when it starts, and terminal shares do not cross
between such instances.
</Aside>

## Metrics

The server sends no metrics unless you point it at a collector. Set `OTEL_EXPORTER_OTLP_METRICS_ENDPOINT`
(the full URL, such as `http://collector:4318/v1/metrics`) or `OTEL_EXPORTER_OTLP_ENDPOINT` (the base URL;
`/v1/metrics` is added), and the server pushes OpenTelemetry metrics there over OTLP/HTTP (JSON). With neither
set, nothing is collected or sent. These are OpenTelemetry's own variables, read by its SDK; `config check` does
not list them.

| Variable | Default | Meaning |
| --- | --- | --- |
| `OTEL_EXPORTER_OTLP_HEADERS` | — | Headers for the collector, `key=value,…` (an API key, say). |
| `OTEL_EXPORTER_OTLP_TIMEOUT` | `10000` | How long one export may take, in milliseconds. |
| `OTEL_METRIC_EXPORT_INTERVAL` | `60000` | How often the numbers are pushed, in milliseconds. |
| `OTEL_METRIC_EXPORT_TIMEOUT` | `30000` | How long one collection may take, in milliseconds; at most the interval. |
| `OTEL_SERVICE_NAME` | `wirebench-server` | The `service.name` resource attribute. |
| `OTEL_RESOURCE_ATTRIBUTES` | — | More resource attributes, `key=value,…`. |

Each process is `service.instance.id` (its instance id, as `admin instances` lists it) with its version as
`service.version`. The instruments are `wirebench.http.requests`, `wirebench.http.duration`,
`wirebench.live.sockets`, `wirebench.host.instances`, `wirebench.sends`, `wirebench.budget.refusals`,
`wirebench.schedules.runs`, `wirebench.repo.lock.wait`, `wirebench.bus.dropped`, `wirebench.bus.lag`,
`wirebench.instances` and `wirebench.db.pool.waiting`. A team appears only by its id
(`wirebench.tenant.id`, or `none`), a request only by its route template, method and status class: never a
URL, a name, an email or anything a request carried. `wirebench.http.duration` has no team id, only the route
and method, so its histogram buckets do not multiply by the number of teams; `wirebench.http.requests` counts by
team. On shutdown the server pushes its last numbers, waiting
at most 5 seconds for the collector.

## Running several instances

A server can run as several instances against one database and one data volume, for availability. One instance is
the default, and it needs nothing below. The instances hear each other through PostgreSQL: live updates, presence and
team and key changes travel over `LISTEN`/`NOTIFY`, pushes to one workspace wait on a PostgreSQL lock, and the rate
limits and the per-team budgets are counted in the database, so a client gets the same limits whichever instance it
reaches. Only a terminal share goes from one instance to another directly.

What it needs:

- **An Enterprise license**, valid or in grace. Without one, a server with `WIREBENCH_SERVER_INSTANCES=multi` refuses
  to start with `server-instances-need-enterprise`. A license that lapses while the instances run does not stop them:
  each logs a warning once an hour, and the next start refuses.
- **On every instance:** `WIREBENCH_SERVER_INSTANCES=multi`; `WIREBENCH_SERVER_INSTANCE_URL`, this instance's own
  address on the private network, such as `http://10.0.0.5:8091`; and the same `WIREBENCH_SERVER_SECRETS_KEY` on
  all of them, since the instances sign the share relay with a key derived from it.
- **PostgreSQL reached directly.** Each instance keeps one listening connection and a small pool of lock connections
  (at most 8). Neither works through a transaction pooler, so both use `WIREBENCH_SERVER_MIGRATION_DATABASE_URL`
  (or the database URL when that is unset), which must be a direct connection, as for the server-running lock.
- **One data volume**, mounted read-write by every instance at the same path.
- **A balancer with a sticky cookie** for at least `/api/v1/host` and `/api/v1/live`: it keeps one browser on one
  instance while that instance lives, and moves it when the instance is gone. The server sets and reads no routing
  cookie of its own. A browser that reaches the wrong instance anyway is told to wait (`4409`) and reconnects; the
  host lease keeps two instances from working on one user's files.
- **A private network** between the instances for the port of `WIREBENCH_SERVER_INSTANCE_URL`. It serves only
  `/internal/v1/`, the terminal-share relay, and must not be reachable from outside; the public port never serves
  `/internal/`. The internal port speaks plain HTTP, so `WIREBENCH_SERVER_INSTANCE_URL` is an `http://` address
  (`https://` is refused): the private network is what protects the traffic. The port binds the URL's host when it
  is an IP address or `localhost`, and every IPv4 interface for a DNS name; `WIREBENCH_SERVER_INTERNAL_HOST` names
  another address to bind. Each relay request carries a token that lasts 30 seconds, works once and only on the
  route it was made for. If the port is reachable from outside by mistake, that token is the only guard: it still
  refuses anyone without the secrets key.

**Health.** `GET /readyz` answers `200` once start-up has finished and while the instance hears the others, and `503`
(`starting`, `reconnecting` or `draining`) otherwise. Point the balancer's health check at it. `/healthz` stays the
check of the database, the data directory and git.

**Draining.** On `SIGTERM` an instance answers `503` on `/readyz` and refuses new sockets. Each browser host it runs
stops, gives up its lease and only then closes its socket, so the tab reconnects at once and the next instance
takes over without a wait. Live-update sockets close with `1012` and the app reconnects. HTTP requests keep being
served until the instance closes, and the whole drain takes at most 10 seconds. Stop instances one at a time.

**Instances.** `wirebench-server admin instances` lists the running instances: id, address, version, age and last
heartbeat. An instance that has not renewed its heartbeat for 60 seconds is treated as gone.

A worked example with Traefik's file provider, two instances on `10.0.0.5` and `10.0.0.6`:

```yaml
http:
  routers:
    wirebench:
      entryPoints:
        - websecure
      rule: 'Host(`wirebench.example.com`)'
      service: wirebench
      tls: {}
  services:
    wirebench:
      loadBalancer:
        # The balancer's own cookie keeps a browser on one instance; Traefik moves it when that instance fails.
        sticky:
          cookie:
            name: wirebench_instance
            secure: true
            httpOnly: true
            sameSite: lax
        healthCheck:
          path: /readyz
          interval: 5s
          timeout: 3s
        servers:
          - url: http://10.0.0.5:8080
          - url: http://10.0.0.6:8080
```

Each instance then has `WIREBENCH_SERVER_INSTANCE_URL` set to its own address with the internal port
(`http://10.0.0.5:8091` and `http://10.0.0.6:8091`), which Traefik does not route. The sticky cookie here covers the
whole origin, which is the simplest way to cover `/api/v1/host` and `/api/v1/live`. Traefik forwards WebSocket
upgrades without more configuration. Any other balancer works the same way: a sticky cookie of its own, a health
check on `/readyz`, and WebSocket upgrades forwarded.

### Per-team budgets

So that one team cannot use up a shared server, the requests the server sends for a team's browser users are
budgeted, every instance together. The defaults are set high enough that a team's own use does not reach them:

- `WIREBENCH_SERVER_TENANT_SENDS_PER_MINUTE` (600, with a burst of a sixth of it). Past it a send fails with
  `tenant-send-budget` and the time to retry; a run started in the browser waits until the budget refills instead,
  each of its requests counting.
- `WIREBENCH_SERVER_TENANT_CONCURRENT_SENDS` (16). Past it a send fails with `tenant-send-concurrency`. A run counts
  as one while it lasts, a WebSocket only while it opens.
- `WIREBENCH_SERVER_TENANT_RUN_SLOTS` (the schedules concurrency by default): scheduled runs one team runs at once.
  Further runs wait their turn and are never refused.

Sends through a paired local agent and scheduled runs' requests do not count against the send budgets. On a
self-hosted server the one team gets the same defaults; [Configuration](#configuration) lists the ranges.

## Custom domain

A team on the hosted service is reached at `https://<slug>.<app-domain>`. On the Enterprise edition, the team's server
admin can serve it at a name of the team's own as well, such as `wirebench.example.com`. Both names then serve the
whole app, and the custom name becomes the team's primary: links in invitations and mail use it. A team has one custom
name at a time. A self-hosted server has no use for this: it sets its own public URL with
`WIREBENCH_SERVER_PUBLIC_URL`, and the routes answer `404` there.

In the desktop app or the browser client, open **Account: Manage teams** and the **Domain** tab. The tab shows only to
server admins of a hosted team whose edition includes custom domains. Enter the name and choose **Claim**. The tab then
shows two DNS records to create at your DNS provider, each with a **Copy** button:

| Type | Name | Value |
| --- | --- | --- |
| `CNAME` | the name | `custom.<app-domain>` |
| `TXT` | `_wirebench.<name>` | `wirebench-domain-verification=<token>` |

The token is made for this claim and shown only to the team's server admins. Keep both records for as long as you use
the name. A name at the top of a domain, such as `example.com`, cannot hold a CNAME record, so it passes only if your
DNS provider flattens the record there (its addresses then match `custom.<app-domain>`'s). A subdomain always works.

The server checks the records every hour while the claim is pending, and every 6 hours once the name is held.
**Check now** checks at once, at most once a minute. The tab shows when the name was last checked, what that check
found, and the state:

| State | What it means | Served? |
| --- | --- | --- |
| Waiting for the DNS records (`pending`) | Claimed; the records have not been seen yet. After 7 days without them the claim expires. | no |
| Records found (`verified`) | Both records are in place and the name is the team's. A certificate for it is on its way. | no |
| Active (`active`) | The certificate is live. The team is served at the name, and it is the primary. | yes |
| Records missing (`failing`) | A re-check did not find the records. The name is still served for now. | yes |
| Lapsed (`lapsed`) | The records were missing for 72 hours. The name is released and no longer served. | no |
| Paused (`paused`) | The team's edition stopped including custom domains. The name is released. | no |
| Expired (`expired`) | The records were not seen within 7 days. Remove the name and claim it again. | no |

A check that cannot reach DNS counts as a failed check: a resolver outage that lasts 72 hours lapses the name as
missing records would. A lapsed or paused name is proved again by a passing check, which moves it back through
**Records found**, so nobody can take over a name that was let go without proving it first. Any number of teams may
claim a name while it is unproved, and the first to pass holds it. A team whose records are right but whose name
another team already holds is told so, never which team.

The server admins get one email, when email is set up, as the name becomes active, starts failing or lapses.

### Identity providers

When the name becomes active, and again if it lapses or is removed, the addresses your identity provider sends people
back to move to the primary name: the OIDC redirect URI, and the SAML entity ID and ACS URL. Update them at the
identity provider, or sign-in through it fails until you do. A sign-in started on the other name completes on the
primary. Password and email sign-in are not affected. A machine paired with the local agent on one name serves pages
on that name only; pair it on the other name too if people use both.

### Removing the name

**Remove…** on the Domain tab drops the claim at once after a confirmation. The name stops being served, the primary
goes back to `<slug>.<app-domain>`, and the proxy drops its route at its next poll. To use the name again, claim it:
the new claim gets a new token, so update the TXT record. An operator can do the same for a support case or abuse with
`wirebench-server admin domains remove --tenant <slug>`; `admin domains list` lists every team's name and state.

## Upgrading

The server applies pending migrations when it starts. To apply them ahead of a restart, run its
`migrate` command. `migrate --check` exits 1 while any are pending.

The first release after 6.1 also moves the data directory's repositories and checkouts into a new subdirectory, at the first start
or in `migrate`, and moves queries to a second database role. Before you upgrade, run `admin tenancy check` from
the new image: it changes nothing, and reports what the upgrade will do and how long it should take (about 2 to 10
seconds per million rows). Stop every server process, back up the database as a superuser or a role with
`BYPASSRLS` (never the app role: under row-level security its dump refuses the tables) and the data directory, then start
the new version. `admin tenancy status` says where the upgrade stands, and `migrate --check` exits 1 until the move
is done: run it where the data directory is mounted, or after the first start. Keep the same
`WIREBENCH_SERVER_SECRETS_KEY` across the upgrade.

The commands for this upgrade, each run as `wirebench-server admin tenancy …` (in the image, `node /app/dist/bin.js
admin tenancy …`) with the server's own environment:

| Command | What it does |
| --- | --- |
| `check` | Reports the PostgreSQL version, the app role, how to back up, what the move will do and how long the migration should take. Changes nothing. |
| `status` | Says where the upgrade stands, and whether the stored data key opens under `WIREBENCH_SERVER_SECRETS_KEY`. |
| `role [--print-sql]` | Creates the app role and grants it its privileges, or prints the statements for an owner that may not create roles. |
| `revert [--accept-unopened \| --abort]` | Undoes the upgrade, below. |

On the team install's `docker-compose.yml`, download the file again and add
`WIREBENCH_APP_DB_PASSWORD=$(openssl rand -hex 24)` to its `.env`; compose refuses to start without it. The file then
gives the server two URLs: `WIREBENCH_SERVER_MIGRATION_DATABASE_URL` as `wirebench`, the owner, and
`WIREBENCH_SERVER_DATABASE_URL` as `wirebench_app`, which the server creates at its first start. An installation
that keeps one URL still starts, and logs that row-level security cannot be relied on for its role; `admin tenancy
role` switches it to two (see the server's README, "Database roles").

To go back, stop every server and run `admin tenancy revert`, which returns the database and the data directory to
the previous version's form, or restore both together from the same backup. It waits three minutes on every run,
resumed runs and `--abort` included, and refuses while any server's connection is open, those of another
installation in another schema of the same database included: stop those too. `--accept-unopened` lets it go on
past values that open under neither key and links it does not follow. The previous version reads
`WIREBENCH_SERVER_DATABASE_URL` only, so point it at the owner's direct URL again, as before the upgrade. Start it
by its own image tag, the release you came from (for example `6.1.0`), never `latest` or `6`: those name the new
version, which would start, migrate and undo the revert. The team install's sequence is in
[Going back](/wirebench/docs/getting-started/team-server/#going-back) on the team server page.

The `wirebench_app` role stays, unused. If you will not upgrade again, drop it with
`DROP OWNED BY wirebench_app; DROP ROLE wirebench_app;`, run in each database it has privileges in. `DROP OWNED BY`
needs the role's own privileges, so run it as a superuser; on a managed database, where the owner is not one, the
owner first runs `GRANT wirebench_app TO <owner>;` (allowed on PostgreSQL 16 and later to the role that created
the app role), and otherwise a superuser or that role runs both. The server's README, "Going back", has the
details.

Restart the server by stopping the old process before starting the new one. A start clears every user's
browser-host lease, so two processes at once would both serve a user's tab for up to 15 seconds. A database restart
does not stop the server, as long as the database is back within about two minutes; after that the server exits
with code 3, for its supervisor to start it again.

On shutdown, the server finishes the repository work already queued before it closes the database, and
closes every live socket. The app reconnects when the server is back.

When the app reports that a server is too old to sync workspaces, upgrade the server. Before a workspace
admin turns team secrets on, everyone in the workspace should update the app.
