A SOAP, REST or gRPC request can have two scripts. The **pre-request** script runs just before the
request is sent and can change it: add a header, sign the body, fill in a field. The **post-response**
script runs when the response arrives and can check it with tests and keep a value for later
requests — a log-in's token, say.

Scripts are TypeScript, and their types come from the request's own contract. A SOAP request's body
is typed from the operation's XSD elements, a REST request's from its OpenAPI operation, and a gRPC
request's from its `.proto` messages. So the editor completes `response.json().orderId`, and a path
that does not exist is an error before anything is sent.

## Write a script

<Steps>

1. Open a request and choose the **Scripts** tab in the strip along the top of the request pane.
2. Choose **Pre-request** or **Post-response** and write the script. Completion, hover and signature
   help come from the request's types; errors are underlined, and counted under the editor.
3. Send the request. The response's **Script** tab shows the tests, whether each passed, and what the
   scripts logged.

</Steps>

A script is saved beside its request, as `<request>.pre.ts` or `<request>.post.ts`, and the request
file names it under `scripts`. See the [project folder format](/wirebench/docs/reference/project-format/).

```ts
// Log in.post.ts: keep the token for the next request, as a secret.
if (response.status === 200) {
  // Typed from the operation's 200 response; `unknown` for a request with no contract, so say what it is.
  const body = response.json() as { access_token: string };
  vars.set('token', body.access_token, { secret: true });
}
test('logged in', () => expect(response.status).toBe(200));
```

```ts
// Checkout.pre.ts: sign the body with a key the request lists under Secrets.
const signature = crypto.hmac('sha256', secrets.get('signing_key'), request.body.text, 'base64');
request.headers.set('X-Signature', signature);
```

The whole API, per protocol and phase, is in the [script API reference](/wirebench/docs/reference/script-api/).

## Scripts on APIs, interfaces and folders

An API, a SOAP interface and each REST or gRPC folder can have the same two scripts, for what every
request inside it needs: fetch a token once, sign every call, check every response for an error field.
When a request is sent, the scripts of each level above it run around its own:

1. the API's (or interface's) script,
2. each folder's, outermost first,
3. the request's own.

Pre-request scripts always run in this order. Post-response scripts do too, unless the API's
**Post-response order** says otherwise (see [below](#post-response-order)). Each pre-request script works on the request the one before it
handed on, so a folder sees the header its API set. A value a script sets with `vars.set` is there for
every script after it in the same send.

- **An API or interface:** the **Scripts** section of the API tab, or the **Scripts** tab of the
  interface viewer.
- **A folder:** **Scripts…** in the folder's menu in the explorer.

A level's script is typed from its protocol's request and response, not from one operation's messages,
because it runs for many operations. Each level lists its own **Secrets** and reads only those. Its
files sit beside its own file: `api.pre.ts` beside `api.yaml`, `interface.pre.ts` beside
`interface.yaml`, `folder.pre.ts` beside `folder.yaml`.

The response's **Script** tab lists each script that ran, in order, under a heading such as
`API "Shop" · pre-request`, with its tests, its log and its failure.

### Post-response order

An API's **Post-response order** setting, in the **Scripts** section of the API tab, chooses which
level's post-response script runs first:

- **Outermost first** (the default): the API's, then each folder's, then the request's.
- **Innermost first**: the request's, then each folder's, then the API's.

It changes only post-response scripts; pre-request scripts always run outermost first. The setting
belongs to the API and is read even when the API's own scripts are switched off, so a collection
imported from Bruno keeps the order its `bruno.json` asked for. A Bruno import sets it to **Innermost
first** for the `sandwich` flow, which is also what Bruno does when no flow is named, and to
**Outermost first** for `sequential`.

## What a pre-request script can change

A pre-request script runs after `${…}` properties are expanded and before the configured auth,
WS-Addressing, WS-Security and signing are applied. So a script's change is signed with the rest of the
request, and the script never sees the configured credentials.

| Protocol | Can change | Cannot change |
| --- | --- | --- |
| REST | method, path, query, headers, body (`body.json`, typed, or `body.text`) | scheme, host, port |
| SOAP | the SOAP body (`body`, typed, or the `envelope` text), headers, SOAPAction | the endpoint's scheme, host, port |
| gRPC | the message (typed), metadata | target, method |

A script that sends the request somewhere else fails with `script-origin-change`, and a header value
with a line break fails with `script-value-invalid`. Either way nothing is sent.

## Tests

`test(name, () => …)` records a test, and `expect` checks a value inside it: `toBe`, `toEqual`,
`toContain`, `toMatch`, `toBeGreaterThan`, `toHaveProperty` and the rest, each with `.not`. A failed
`expect` fails its test and the script carries on. Tests count as the request's assertions, in the app,
in a sequence and in `wirebench run`.

## Values for later requests

`vars.set(name, value)` keeps a value that later requests read as `${#Sequence#name}`:

- **A single send in the app** keeps it in the project's session, in memory, until the project closes.
  The explorer lists the session's values under **Values**, with **Clear values** (the
  `Scripts: Clear Session Values` command does the same).
- **A sequence run** keeps it for the steps after it, as a transfer would.
- **`wirebench run`** keeps it for the requests after it, in run order.

A value from a script comes from a response, so it is held to the same rules as a sequence's
transfers: it is used exactly as set, escaped where it lands, can't choose where a request goes, and
can't carry a line break into a URL or header. Mark it `{ secret: true }` when it is a credential: it is
masked in the log, History, reports and the Values list, which shows it only as `(secret)`.

## Secrets

- Credentials configured on the request, folder or API are applied after the pre-request script. A
  script never sees them.
- A `${secret:name}` in the request's text reaches the server as its value, but the script sees a
  placeholder in its place.
- `secrets.get(name)` returns a secret's value only when the request lists that name under **Secrets**
  on the Scripts tab (`scripts.secrets` in the file). Listing one is a change a reviewer sees. Every value
  a script reads this way is masked everywhere it could appear.

## What a script can't do

A script is code from the project, and it runs with no capabilities. It can't reach the network, read
a file or the keychain, or touch another project or the app. It runs in a sandbox on its own thread,
fresh for each run, with limits:

| Limit | Default |
| --- | --- |
| Time | 1 second per script (**Timeout**, up to 10 seconds) |
| Memory | 64 MiB |
| Log | 1,000 lines, 64 KiB |
| Tests | 1,000 |
| Values | 100, each up to 64 KiB |
| Script file | 256 KiB |

TypeScript's erasable syntax only: no `enum`, `namespace`, parameter properties or decorators. There is
no `setTimeout`, `fetch` or `require`.

## When a script fails

- **A pre-request script** throws, times out or breaks a rule: the request is not sent, and the error
  names the script's file, line and column. The scripts after it do not run.
- **A post-response script** throws: the response is kept and shown, and the request is reported as
  errored, with the error on the **Script** tab. The post-response scripts after it still run, and the
  first failure is the one reported.
- **A type error** stops the send before anything is resolved or sent (`script-type-error`).
- **A missing script file** stops the send too (`script-file-missing`): the request says it has a script
  that is not there. A missing API, interface or folder script stops every request inside it.

## Switch scripts off

Clear **Run these scripts** to keep a request's scripts without running them. The request is sent as if
it had none, isn't type-checked, and its result says its scripts were off. An API's, an interface's and a
folder's scripts are switched on and off on their own: switching off a request's scripts leaves its
API's and folders' running.

## Scripts from other clients

A Postman collection's, an Insomnia export's, a Bruno collection's and a Hoppscotch export's scripts
are imported onto the request, folder or API they were on, and run through a layer that gives them the
other client's own names: `pm` for Postman, `insomnia` and `$` for Insomnia, `bru`, `req` and `res`
for Bruno, `pw`, `hopp` and `pm` for Hoppscotch. They are JavaScript, checked for syntax only, and run
in the same order as they did in the client. Scripts exported from Thunder Client are still saved as
text under `imported-scripts/` and never run.

**Imported scripts are switched off.** A collection from elsewhere is code nobody on the team has read
yet. A request with them shows a banner — "These scripts are off. Read them, then switch them on." — and
**Switch on**. **Switch on scripts…** on an API, a folder or an interface switches on its own scripts and
those of every folder and request beneath it, after a confirmation that names them. The import summary
says which folders and requests have scripts and lists the calls in them that cannot run.

A layer is only a vocabulary over the Wirebench script API, so it can do nothing a Wirebench script
cannot. Three rules hold for every layer.

**Variables.** A client has more variable scopes than Wirebench's two. A read checks the run's `vars`
first, then the read-only `props`. A write goes to `vars`, whatever scope the script named
(`environment`, `collectionVariables`, `variables`, `baseEnvironment`): it lasts for the run, later
requests read it as `${#Sequence#name}`, and it is never written to a project or environment file. A
script that relied on a write surviving after the app closed loses that. A request that read
`{{ name }}` in the client keeps reading `${name}` after the import, which is a project property or
environment variable; point it at `${#Sequence#name}` to read a value a script set.

**Unsupported calls.** A call the sandbox cannot honour — sending requests, loading modules, reading
files, waiting, cookie writes, the vault — fails when it is called, with `script-unsupported` naming it.
The import summary lists the scripts that call one.

**Run control.** `setNextRequest` and `skipRequest` steer a run as `execution` does ([below](#steer-a-run)):
they are obeyed in API and folder runs and ignored, with a note in the log, everywhere else.

### Postman scripts

A Postman collection's `prerequest` and `test` scripts are imported where they were: the collection's on
the API, each folder's on its folder, and each request's on the request.

The layer covers what collections mostly use: `pm.test`, `pm.expect` with the common chai chains,
`pm.response` (`code`, `status`, `headers.get`, `json()`, `text()`, `responseTime`,
`to.have.status`), `pm.request` (`url`, headers, `body.raw`), `pm.info.requestName`, the `pm.*.get`
and `pm.*.set` variable calls (all kept as the run's values), `CryptoJS` hashes, HMACs and Base64,
`btoa` and `atob`. `pm.execution.setNextRequest`, `postman.setNextRequest` and
`pm.execution.skipRequest` steer a run. Anything else — `pm.sendRequest`, `pm.cookies.jar()`,
`pm.visualizer`, `require` — fails when it is called, with `script-unsupported` naming it.

A script can't send a request, so a `pm.sendRequest` call needs rewriting:

- A login whose token the next request uses is a [sequence](/wirebench/docs/guides/sequences/) step with a
  transfer.
- A token fetched before every request is the request's or its API's OAuth2 auth.

### Insomnia scripts

An Insomnia export's pre-request and after-response scripts are imported onto their request or folder.
Insomnia has no script level above a folder, so there is none on the API.

`insomnia` and `$` are the same object as `pm` in the Postman layer, with two more members:
`baseEnvironment` and `parentFolders` read like `environment` and write to the run's `vars`.

| Insomnia | In Wirebench |
| --- | --- |
| `insomnia.test`, `insomnia.expect` | Supported, as `pm.test` and `pm.expect` |
| `insomnia.response` (`code`, `status`, `headers`, `json()`, `text()`, `responseTime`) | Supported |
| `insomnia.request` (`url`, headers, `body`) | Supported |
| `insomnia.variables`, `environment`, `baseEnvironment`, `collectionVariables`, `globals` | Supported; reads check `vars` then `props`, writes go to `vars` |
| `insomnia.iterationData` | Supported; reads the current data row of a [data-driven run](/wirebench/docs/guides/runner/), and has no `set` |
| `insomnia.info.requestName` | Supported |
| `insomnia.execution.setNextRequest`, `skipRequest` | Supported; obeyed in API and folder runs only |
| `insomnia.cookies` reads | Supported; they return nothing, as no cookie is visible to a script |
| `insomnia.cookies` writes (`set`, `unset`, `clear`) | `script-unsupported` |
| `insomnia.vault.get` | `script-unsupported` |
| `insomnia.sendRequest` | `script-unsupported`; use a [sequence](/wirebench/docs/guides/sequences/) step or OAuth2 auth |
| `insomnia.require`, `require` | `script-unsupported` |

An Insomnia unit-test suite (the Tests tab) is reported on import and not run: it targets a request by
id outside any script.

### Bruno scripts

A Bruno collection's scripts are imported where they were: `collection.bru` on the API (on both the
REST and the gRPC API when it has both), each `folder.bru` on its folder, and each request on the
request. A request's `script:post-response` and its `tests` block become one post-response script,
the tests after the script.

Bruno's layers run in an order set by `scripts.flow` in `bruno.json`. Wirebench stores it as the
API's [post-response order](#post-response-order): `sandwich`, or no flow, runs post-response scripts
innermost first; `sequential` runs them outermost first. Pre-request scripts run outermost first
either way.

Three things stay as text under `imported-scripts/`, with a note in the report naming the file: the
`.js` module files a collection holds, scripts on a WebSocket request or a WebSocket-only folder, and a
collection script when the collection has no REST or gRPC request to hold it.

| Bruno | In Wirebench |
| --- | --- |
| `test`, `expect` with the common chai chains | Supported |
| `expect(x).to.have.jsonSchema(schema)`, also after `.not` | Supported; see [below](#jsonschema) |
| `res.status`, `res.body`, `res.headers`, `res.responseTime`, `getStatus()`, `getBody()`, `getHeader()`, `getResponseTime()` | Supported; `res.body` is parsed JSON for a JSON response and text otherwise, and `res.headers` has lower-case names |
| `req.getUrl`, `setUrl`, `getMethod`, `setMethod`, `getHeader`, `getHeaders`, `setHeader`, `deleteHeader`, `getBody`, `setBody` | Supported |
| `bru.getVar`, `setVar`, `hasVar`, `deleteVar`, `getEnvVar`, `setEnvVar`, `getCollectionVar`, `getFolderVar`, `getRequestVar` | Supported; reads check `vars` then `props`, writes go to `vars` |
| `bru.interpolate` | Supported with limits; see [below](#interpolate) |
| `bru.setNextRequest`, `bru.runner.skipRequest`, `bru.runner.stopExecution` | Supported; obeyed in API and folder runs only |
| `req.setTimeout`, `getTimeout`, `setMaxRedirects`, `onFail`, `disableParsingResponseJson` | `script-unsupported`; use the request's **Settings** |
| `bru.cookies` | `script-unsupported` |
| `bru.sendRequest` | `script-unsupported`; use a [sequence](/wirebench/docs/guides/sequences/) step or OAuth2 auth |
| `bru.sleep` | `script-unsupported` |
| `require` | `script-unsupported` |

#### interpolate

`bru.interpolate(text)` replaces each `{{name}}` with the run's value of `name` (its `vars`, then the
project's properties). Strings, arrays and plain objects are walked. Two forms are left exactly as
written, because a script cannot compute them: a dynamic `{{$name}}`, and `{{process.env.NAME}}`. A name
nothing holds is also left as written.

#### jsonSchema

`expect(value).to.have.jsonSchema(schema)` checks the value against a JSON Schema and fails the test,
listing the first problems with their paths. A check has a budget of schema nodes: when a very large
body or schema uses it up before the check finishes, the expectation fails and its message says so
(`the check could not finish`) rather than passing unchecked. Narrow the schema or the value if you
meet it.

As with every layer, a value a script stores lasts for the run and the next request reads it as
`${#Sequence#name}`; a `{{name}}` in a request becomes `${name}`, which reads the environment.

### Hoppscotch scripts

A Hoppscotch collection's scripts are imported where they were: the collection's on the API, each
folder's on its folder, each request's on the request. A request's test script becomes its
post-response script. Pre-request scripts run outermost first, as in every layer.

`pw` and `hopp` are the Hoppscotch names; `pm` is the Postman object without `collectionVariables` and
`iterationData`, whose members are unsupported, with `pm.visualizer.set` and the run-control calls
`pm.execution.setNextRequest` and `skipRequest` unsupported too.

| Hoppscotch | In Wirebench |
| --- | --- |
| `pw.test`, `hopp.test` | Supported |
| `pw.expect` | Supported; the Jest matchers `toBe`, `toBeType`, `toInclude`, `toHaveLength` and `toBeLevel2xx` to `toBeLevel5xx`, each with `.not` |
| `hopp.expect` | Supported; the same Jest matchers and the chai chain (`.to.equal` and the rest) |
| `pw.response` | Supported; `status`, `headers` (a list of `{ key, value }` rows) and `body`, parsed JSON for a JSON response and text otherwise |
| `hopp.response` | Supported; `statusCode`, `statusText`, `headers`, `responseTime`, and `body.asJSON()` and `body.asText()` |
| `hopp.response.body.bytes` | `script-unsupported` |
| `pw.env` | Supported; `get`, `set`, `unset`, `resolve` and `getResolve`. `get` is plain: an unset name gives `undefined` and `<<name>>` is not expanded. `resolve` expands `<<name>>` (an unset name becomes empty, nested names up to 10 levels). Writes go to `vars` |
| `hopp.env`, `hopp.env.active`, `hopp.env.global` | Supported; `get`, `getRaw`, `set` and `delete`. `get` expands `<<name>>`, `getRaw` does not, and both give `null` for an unset name |
| `hopp.env.reset`, `getInitialRaw`, `setInitial` | `script-unsupported` |
| `hopp.request` reads: `url`, `method`, `headers`, `params`, `body`, `variables` | Supported; `headers` and `params` are lists of `{ key, value }` rows, `body` is `{ contentType, body }` |
| `hopp.request` writes: `setUrl`, `setMethod`, `setHeader`, `setHeaders`, `removeHeader`, `setParam`, `setParams`, `removeParam`, `setBody`, `variables.set` | Supported in a pre-request script only; `setBody({ contentType, body })` also sets `Content-Type` |
| `hopp.request.setAuth`, `hopp.request.auth` | `script-unsupported`; use the request's **Auth** tab |
| `pm.*` | Supported as in the Postman layer, except the rows below |
| `pm.collectionVariables`, `pm.iterationData`, `pm.visualizer`, `pm.execution.setNextRequest`, `pm.execution.skipRequest` | `script-unsupported` |
| `hopp.cookies`, `pm.cookies.jar` | `script-unsupported` |
| `hopp.fetch`, `pm.sendRequest` | `script-unsupported`; use a [sequence](/wirebench/docs/guides/sequences/) step or OAuth2 auth |
| `pm.vault`, `pm.require`, `require` | `script-unsupported` |
| A top-level `import` | Refused before the script runs; a bare `export {};` line is ignored |

A value a script stores lasts for the run; see [Values for later
requests](#values-for-later-requests). A `<<name>>` in a request becomes `${name}`, which reads the
environment, so the next request reads a stored value as `${#Sequence#name}`.

## Steer a run

In an API or folder run (`wirebench run`), a script can choose what the run sends next:

```ts
// post-response: poll until the job is ready, at most five times
const tries = Number(vars.get('tries') ?? '0') + 1;
vars.set('tries', tries);
if ((response.json() as { ready: boolean }).ready === false && tries < 5) {
  execution.setNextRequest('Job status');
}
```

- `execution.setNextRequest(name)`:
  - After this request, the run goes on at the first selected request with that name.
  - Requests a jump passes over are reported as skipped, and a jump back runs requests again.
  - `null` ends the run, and the requests after it are reported as skipped.
  - The last call wins, across every level's scripts.
- `execution.skipRequest()`:
  - Pre-request scripts only. The request isn't sent, and is reported as skipped.
  - The rest of its pre-request scripts don't run.

The name must be one of the requests the run selected. Any other name errors the request with
`script-next-unknown`, and the run stops there. A run can jump at most 1,000 times
(`script-jump-limit`), and the limit can't be raised or turned off.

A single send and a sequence step don't obey these calls. They log a line saying the call was ignored.
A sequence's order is the sequence's own.

## In CI

`wirebench run` runs every selected request's scripts, and its API's, interface's and folders', with and
without `--sequence`. It type-checks them all before it sends anything, and a type error exits 2 with the file, line and column. Script tests
appear in every reporter as assertions, and the log goes to stderr with `--verbose` and into the JSON
report as `scriptLog`.
