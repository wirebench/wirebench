On a machine IT manages, a **policy file** sets preferences the user cannot change: the proxy every
send goes through, the CA bundle that adds your organization's trust anchors, the minimum TLS version,
and whether Wirebench checks for updates. Every setting the file names is shown in
**Settings** as **Managed**, and a note at the top of each Settings section names the file.

## Where the file goes

Wirebench reads `policy.yaml` from a system location only an administrator can write:

| OS | Path |
| --- | --- |
| Windows | `%ProgramData%\Wirebench\policy.yaml` (usually `C:\ProgramData\Wirebench\policy.yaml`) |
| macOS | `/Library/Application Support/Wirebench/policy.yaml` |
| Linux | `/etc/wirebench/policy.yaml` |

The file is read once, when Wirebench starts. After you deploy or change it, users need to restart
Wirebench. Make the file and its folder writable by administrators only — anyone who can write it can
change what it locks.

## What goes in it

The file uses the same YAML shape as the user's own preferences. Every key present is locked; anything
left out stays the user's choice.

```yaml
version: 1
proxy:
  mode: manual # none | system | manual
  host: proxy.corp.example
  port: 8080
  username: svc-wirebench
  excludes: [localhost, '*.corp.example', 10.0.0.0/8]
ssl:
  minVersion: TLSv1.2 # TLSv1.2 | TLSv1.3
  caBundlePath: /etc/ssl/certs/corp-ca.pem
updates:
  checkOnLaunch: false
  channel: stable # stable | preview
areas:
  ssh: false # switch the SSH area off on this machine (see below)
```

These are the keys a policy can lock:

| Key | Values |
| --- | --- |
| `proxy.mode` | `none`, `system` or `manual` |
| `proxy.host`, `proxy.port`, `proxy.username` | The manual proxy's host, port and user name |
| `proxy.excludes` | Hosts that bypass the proxy: names, `*.wildcards`, IPv4 CIDR blocks or `localhost` |
| `ssl.minVersion` | `TLSv1.2` or `TLSv1.3` |
| `ssl.caBundlePath` | An absolute path to a PEM file of extra trust anchors, or `''` to lock "no bundle" |
| `updates.checkOnLaunch` | `true` or `false` |
| `updates.channel` | `stable` or `preview` |

### Areas

The `areas` section is the one section that is not a preference: it switches a desktop area off on the
machine, whatever the `WIREBENCH_AREAS` environment variable says. The ids are `explorer`,
`environments`, `search`, `history`, `wss`, `ssh`, and the three that ride with the SSH area,
`local-terminal`, `telnet` and `serial`. Only `false` is accepted: a policy switches off and never on,
so `ssh: true` is ignored and listed in the Settings note. An area that is off is removed from the
activity bar, the palette and the app's IPC surface; **Settings → Features → Areas** shows it as
**Managed** with _Set by your organisation_. The [feature switches](/wirebench/docs/guides/feature-switches/#areas)
guide has the detail.

The proxy password is never part of a policy: it's kept in each user's OS keychain, so users with a
locked manual proxy still enter their own password in **Settings → Proxy**.

A CA bundle named by the policy is trusted without the user picking it, because the policy file sits
where only an administrator can write. The bundle adds to the system's trust store; it never replaces
it.

## What users see

- Each locked setting is read-only and marked **Managed**. The CA bundle's **Browse…** and
  **Clear** buttons are unavailable while it is locked.
- A locked row offers no **Reset**, and **Reset … to defaults** in a section's **•••** menu leaves locked
  values in force.
- The user's own preferences file keeps only their own values. If the policy is removed, their
  previous settings come back at the next start.

## When something is wrong

- **A key that can't be locked**, or a value that isn't valid (a relative CA bundle path, a proxy mode
  that isn't one of the three), is ignored. The note in Settings lists every ignored key, so you can
  see which ones had no effect; the rest of the policy still applies.
- **A file that can't be read or isn't valid YAML** locks nothing. Settings shows an error naming the
  file and the reason.

<Aside type="tip" title="Testing a policy">
Try a policy on one machine before rolling it out: deploy the file, restart Wirebench, and check that
**Settings → Proxy**, **SSL / TLS** and **Updates** show the settings you expect as locked, and that the
note at the top lists no ignored keys.
</Aside>
