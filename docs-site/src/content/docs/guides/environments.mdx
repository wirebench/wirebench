Environments let one request work against several deployments — local, staging, production —
without editing the URL or the body each time. You set variables once, in a scope, and reference
them with `${...}` inside URLs, headers, envelopes and bodies. The syntax itself, and the full
precedence rules, are covered in
[Property expansion syntax](/wirebench/docs/reference/property-syntax/); this page is about managing
environments day to day.

## Open the Environments view

Choose **Environments** in the activity bar. It lists **Globals**, **Workspace**, and every
environment you've added — both workspace-level environments and any linked project's own. Each
entry opens a page with a table of variables.

## Scopes, from broadest to narrowest

- **Globals** — available everywhere, referenced as `${#Global#name}`. The broadest scope; a
  workspace or environment variable with the same name wins over it.
- **Workspace** — available to every project in the workspace, as `${#Workspace#name}`. An active
  environment's variable of the same name wins over it.
- **Environment** — the variables of whichever environment is active, as `${#Env#name}`. This is
  the scope you switch between deployments with.

The shorthand `${name}` (no `#Scope#`) resolves through Env, then Workspace, then Global —
whichever scope defines it first.

## Add and switch environments

<Steps>

1. In the Environments view, choose **Add environment**. It opens on the new environment's page
   with a default name.
2. Click the name to rename it, or right-click the row and choose **Rename**. Press
   <kbd>Enter</kbd> to commit, <kbd>Escape</kbd> to cancel.
3. To make it the one requests use, open the environment switcher in the title bar and choose it
   from the list.

</Steps>

Each project has one active environment of its own. The switcher is labelled with the project it
acts for, the project of the request tab you last focused, and every request tab of that project
picks the choice up immediately. Moving to a tab of another project shows that project's own
choice, or **No environment** if it has none; there's no per-tab environment. Before any request
tab has been focused the switcher reads **No project** and is disabled.

## Choose which projects an environment applies to

A workspace environment applies to every project by default. When a workspace holds several
projects, narrow it so a project is offered only the environments meant for it: a `Billing
sandbox` that a CRM request can never pick by accident.

<Steps>

1. Open the environment's page. Under the name, **Applies to** reads **All projects** or
   **Selected projects**.
2. Choose **Selected projects**. A list of the workspace's projects appears with every one ticked,
   so nothing drops out until you clear a box.
3. Clear the projects it should not apply to.

</Steps>

- The switcher lists two groups: **All projects** for the environments that apply everywhere, then
  a group named after the current project for the environments scoped to it. **Next environment**
  cycles through the same list.
- The Environments view shows the project names as small chips on a scoped environment.
- The **Active** toggle and a row's activate button act for the current project, and are disabled
  with a tooltip when the environment does not apply to it.
- The **Endpoints** table lists only the interfaces of the projects in scope. Overrides you typed
  for a project that leaves the scope stay saved and come back when the project is added again.
- Narrowing a scope drops the active choice of any project that is left out. Removing an
  environment does the same.
- Duplicating an environment keeps its scope. When a linked project brings environments of its own
  they are created scoped to that project, and one that already exists in the workspace gains the
  project in its scope.
- Removing a project from the workspace removes it from every scope. An environment left with no
  project is kept, shown as **No project**, and the removal dialog names it first, so nothing you
  typed is lost. Choose **Selected projects** again to give it projects.

The scope is saved in the environment's file as `projects`, a list of project ids; an environment
without it applies to every project. A teammate on an older build sees a scoped environment as
applying to every project, and if they edit it the scope is lost.

## Colour an environment and protect it

Production should look different from local, and should be hard to hit by accident. Both settings
sit under the name on an environment's page.

- **Colour** — pick one of the eight swatches, type a custom `#rrggbb`, or choose **None**. The
  environment switcher shows the colour as a dot beside each environment's name. The active
  environment's colour also runs along the top of the editor tab strip, so it stays in view while
  you work.
- **Protected** — tick it, and every send under this environment asks first. A warning box
  names the environment, and **Cancel** is the default, so a stray <kbd>Enter</kbd> sends nothing.
  This covers a send from the editor, a History re-send and an HTTP Log resend. A sequence run asks
  once, before its first step. **Send to environments…** asks once for all the protected
  environments in the batch; if you cancel, the other environments are still sent. The switcher
  shows a lock beside a protected environment.

Inside a workspace, a workspace environment also counts as protected when the linked project
environment of the same name is protected. Duplicating an environment keeps its colour and its
protection.

Both settings are saved in the environment's file as `color` and `protected`. The command line acts
on `protected` too:

- `wirebench run` prints a warning before sending under a protected environment.
- `wirebench run --refuse-protected` exits with code 2 instead, before anything is sent. Use it in
  a pipeline that must never reach production.
- `wirebench mcp` refuses a protected environment unless the call passes `allowProtected: true`. See
  [Agents and MCP](/wirebench/docs/guides/agents-mcp/).

## Set variables

Each scope's page (Globals, Workspace, or an environment) has its own table: name, value, and a
**Secret** flag.

<Steps>

1. Add a row and type a name and value.
2. Turn on **Secret** for anything sensitive — a token, a password, an API key. See
   [Secrets](/wirebench/docs/guides/secrets/) for how secret values are stored and masked.
3. Reference it anywhere property expansion is read — the address bar, headers, a JSON body, a
   SOAP envelope — with `${#Env#name}`, `${#Workspace#name}`, `${#Global#name}`, or the shorthand
   `${name}`.

</Steps>

An unresolved reference — a typo, or a variable that only exists in a different environment —
shows up as a row in **Problems** when you send, naming the exact `${...}` text it couldn't
resolve.

### Disable a variable without deleting it

Every row has an enabled checkbox. Unticking it makes property expansion treat the variable as
absent — a reference to it falls through to the next scope in the precedence chain (or is left
unresolved if nothing else defines it) — while its value stays saved. This is the quickest way to
try a request without a variable, or to keep a rarely used value around without deleting it.

## Current values

Every variables table — Globals, Workspace, a project and each environment — has a **Current**
column beside **Value**. A current value replaces the committed value for this session only: the store
is never written to the project, the workspace or the keychain, and it is gone when you quit. A
request that is sent records what it sent, in History and the HTTP Log, as it would for a committed
value: keep credentials in `${secret:…}` references.

- An empty Current cell shows the committed value as a placeholder; that value applies.
- Type into the cell and press <kbd>Enter</kbd> to set a current value. The variable's name gets a
  dot, and every send, preview and the code panel use the current value.
- Empty the cell, or enter the committed value, to go back to it. The reset button in a row resets
  that variable; **Reset current values** in the column header resets the whole table.
- A disabled variable stays absent; its current value does not apply.
- A current value may itself contain `${...}`, which is expanded like any other value.
- Rename a variable and its current value follows; delete it and the current value goes too.
- A secret's Current cell is masked like its Value until you show secrets.
- Current values don't exist on the command line; `--var` plays that part.

## Endpoint overrides

An environment's page also has an **Endpoints** table, one row per SOAP interface and REST or gRPC
API the workspace can reach. Filling in a row redirects every request under that interface or API
to the address you type, instead of the one the WSDL or the API's own base URL declares — useful
for pointing an imported definition at a different deployment of the same service.

![The uat environment's page, with the Calculator interface's endpoint override set to a UAT address](/wirebench/docs/images/environments/endpoint-override.png)

A row shows which layer is currently winning when more than one could apply — for example, a
linked project's own environment override beats a workspace environment's override for the same
interface. A request sent under an overridden interface shows a badge next to its endpoint field
so you can tell, without opening Environments, that something is redirecting it.

## Send to several environments

To check that a request behaves the same on dev, test and prod, send it to all of them at once
instead of switching the active environment between sends. This works for SOAP and REST requests.

<Steps>

1. In the request's editor, choose **Environments…** next to **Send**, or run
   **Request: Send to Environments…** from the command palette.
2. Tick the environments to send to — two or more, up to ten. The active environment starts
   ticked.
3. Choose a **Baseline**: the environment the others are compared against. It defaults to the
   active environment.
4. Choose **Send**.

</Steps>

The environments offered are the workspace's that apply to the request's project — the same ones the
environment switcher lists and that decide where a normal send goes. A project's own environment takes part only through the
workspace environment it is linked to. With fewer than two such environments the action is
unavailable, and its tooltip says why.

Each environment gets the request exactly as a normal send with that environment active would
build it — its endpoint override or base URL, its variables, its auth and TLS settings — and your
unsaved edits go with every one. The sends run in parallel, and **the active environment does not
change**. One environment failing (an unresolved property, no endpoint, a refused connection)
does not stop the others; **Cancel** stops the ones still running and opens no Compare tab. While
a comparison runs, a second one for the same request cannot be started. The picker remembers your last
selection for each request until you close the app.

The results open in a **Compare** tab:

- one column per environment, the baseline marked, with the URL it went to, the status, the time,
  the size and the response body;
- a line per other environment reading **same body**, **body differs**, **status differs** or
  **failed** against the baseline, so a wide comparison can be read at a glance;
- below, the baseline diffed against one other environment, chosen from a list: response headers
  side by side, then the two bodies in a diff editor. Bodies are pretty-printed first, so a
  difference in formatting alone is not reported as a change.

Every individual send is also recorded in **History** and the **HTTP Log**, one entry per
environment — closing the Compare tab loses nothing. A History entry reads
`<request> · <environment>`; in the HTTP Log, tell the rows apart by the URL each one went to.

## On the command line

`wirebench run`, `wirebench call` and the MCP server pick an environment with `--env <name>` (MCP:
the `environment` argument), and they follow the same scopes as the app.

- Only environments that apply to the project can be picked. Naming one that exists but is scoped
  to other projects exits with code 2 and `environment-out-of-scope`, and the message lists the
  environments that do apply: `the environment "Billing sandbox" does not apply to this project;
  environments for it: Shared`.
- `--env` is required only when at least one environment applies to the project. A project whose
  scoped environments all belong to other projects runs without it, and a missing `--env` on a
  project that has some exits with `environment-required`.
- The command line never reads the app's active environment, so it is always chosen explicitly.
