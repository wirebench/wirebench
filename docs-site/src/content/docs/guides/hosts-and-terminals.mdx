A workspace can describe the machines its APIs run on: servers, bastions, jump hosts. You write them
down once, in groups, and open an interactive SSH terminal to any of them from the **Hosts** view,
the command palette, or quick-open. The user, port, key and jump host are set on a group and
inherited by every host under it, and the credentials never leave Wirebench's main process.

<Aside type="note">
This part of the SSH area covers hosts, terminals and split terminals, files, port forwarding and snippets. See
[What is not here yet](#what-is-not-here-yet) for what comes later.
</Aside>

## The hosts file

Hosts live in `hosts.yaml`, beside `workspace.yaml` in the workspace folder, so they travel with the
workspace the same way the rest of it does (git, or the server). A missing file is an empty list of
hosts.

```yaml
version: 1
groups:
  - id: prod
    name: Production
    tags: [prod]
    ssh:
      user: deploy
      port: 22
      jump: bastion
      auth: { key: '${secret:prod_key}' }
    groups:
      - id: eu
        name: EU
        hosts:
          - id: api-1
            name: api-1
            address: 10.0.1.5
            ssh:
              auth: { password: '${secret:api1_pw}' }
hosts:
  - id: bastion
    name: bastion
    address: bastion.example.com
    tags: [jump]
    ssh:
      user: ops
      auth: { agent: true }
```

You normally don't edit the file by hand: the Hosts view reads and writes it. If you do, a problem in
the file is shown in the Hosts view and in the Problems tab (source **hosts**), and the rest of the
workspace still opens.

The rules:

- `version` is `1`. Keys Wirebench doesn't know are refused, as in `workspace.yaml`.
- `id` is stable and unique across the whole file, made of lowercase letters, digits and hyphens
  (`api-1`, `eu`). `name` is free text and can change; the id is what `jump` points at.
- `ssh` on a group or a host holds `user`, `port`, `jump`, `auth`, `keepAlive` and
  `connectTimeout` (both in seconds), and `forwardAgent` (see [Agent forwarding](#agent-forwarding)).
  Every field is optional at every level. A host must end up
  with a `user` and an `auth`, from itself or a group above it; otherwise connecting says which
  field is missing and where it can be set. The port defaults to 22, the keep-alive to 15 seconds
  and the connect timeout to 20 seconds.
- `tags` are plain strings. They feed the Hosts filter, the palette and quick-open, and carry no
  behaviour.
- `jump` names the id of another host. Chains are followed through that host's own `jump`; an
  unknown id or a loop is refused when the file is read.
- `auth` is exactly one of `{ password }`, `{ key, certificate?, passphrase? }` or `{ agent: true }`.
  The agent option signs with your local SSH agent; `certificate` is the key's OpenSSH certificate
  (see [Certificates](#certificates)).
- `env` on a group or a host maps variable names to values; see
  [Environment variables](#environment-variables).

## Inheritance

Settings flow from the root of the tree down, one field at a time: a value set on a nearer level
wins. A host under **Production** and **EU** takes the user, port and jump host from **Production**
unless **EU** or the host sets its own.

`auth` counts as one field, not a merge of its parts. A host that sets `auth: { password: … }` drops
the group's key completely instead of adding a password to it.

In the host form, a field you haven't set shows the value it inherits, greyed, with where it came
from, for example `from prod` (or `default` for the built-in values). Turn on the override switch next to the field to edit the
field on that host; turn it off again to go back to inheriting. Changing a group's key changes every
host under it that doesn't override it.

## Secrets

Credentials are never written in `hosts.yaml`. `${secret:NAME}` is the only form accepted: a literal
password, key or passphrase is refused when the file is read or saved, so the file can be committed
and shared. `NAME` follows the same rules as everywhere else: letters, digits and underscores, not
starting with a digit. A `key` resolves to the private key _text_ (the secret holds the PEM), not to
a path, so the workspace works on every machine that holds the secret.

SSH secrets belong to the **workspace** on your machine, not to a project, because a host belongs to
the workspace. In the host form, the password, key and passphrase fields are pickers over the known
secret names, each marked with where it comes from. **Set value…** stores a value for a name on this
machine; the field is write-only and the value is never shown again or sent back to the interface.

When you connect, a name resolves like any other secret in the app: a name mapped to an
[external secret manager](/wirebench/docs/guides/secrets/#secrets-from-external-managers) comes from
its source, and any other name comes from the value stored for this workspace on this machine. A
missing value fails the connect with `secret-missing` and the name. Project secrets don't apply: a
secret you set on a project is not visible to a host.

## Certificates

If your organisation runs an SSH certificate authority, the servers trust the CA instead of each
person's key, and you sign in with your key plus the short-lived certificate the CA issued for it
(the `-cert.pub` file `ssh-keygen -s` writes). Give the key a `certificate`, a secret holding that
certificate line:

```yaml
ssh:
  user: alice
  auth:
    key: ${secret:work_key}
    certificate: ${secret:work_key_cert}
```

On connect Wirebench offers the certificate first and then the key alone, as `ssh` does, so a server
that also lists the key in `authorized_keys` still lets you in. `certificate` is part of `auth`, so a
group's key and certificate are inherited together.

Before connecting, the certificate is checked against the key and the clock. A certificate outside
its validity window fails with `ssh-cert-expired` and says when it was valid (for example
`The certificate has expired: it was valid from 2026-10-01 09:00:00 UTC to 2026-10-01 17:00:00 UTC`);
ask your CA for a new one. A host certificate, or a certificate issued for another key, is refused too.
Ed25519, ECDSA and RSA keys are supported; certificates for security keys (`sk-…`) are not.

**In the keychain.** A key's row has **Attach certificate…**: paste the certificate and Wirebench
checks that it is a user certificate for that key, then stores it as the secret `<key>_cert`, next to
`<key>_passphrase`. The row then shows the certificate's key ID, its principals (the user names it is
valid for) and its validity window, with a badge when it has expired, is not valid yet or belongs to
another key. When a certificate is renewed, **Replace certificate…** stores the new one under the same
name, so every host that uses it picks it up. In the host form, choosing a key that has a `<key>_cert`
fills in **Certificate secret** for you.

Trusting servers by a host CA (`@cert-authority` in `known_hosts`) is separate from this: host keys are
still trusted as described in [Host keys](#host-keys).

## Environment variables

A group or a host can set environment variables for the shells it opens: a locale, a terminal
setting, an application profile, a proxy.

```yaml
groups:
  - id: prod
    name: Production
    env:
      LANG: en_US.UTF-8
      APP_PROFILE: prod
      API_TOKEN: '${secret:prod_api_token}'
    hosts:
      - id: api-1
        name: api-1
        address: 10.0.1.5
        env:
          LANG: C.UTF-8
```

- Variables merge by name down the tree, and a nearer level wins for each variable. **api-1** above
  gets `LANG=C.UTF-8` from itself and `APP_PROFILE` and `API_TOKEN` from **Production**.
- A name is letters, digits and underscores, not starting with a digit. A value is text, or a whole
  `${secret:NAME}` token that resolves when you connect, like a password. A token inside other text is
  refused, so it is never sent as written.
- The variables are sent as SSH `env` requests when a terminal opens, before the shell starts. A
  server keeps only the names its `AcceptEnv` setting allows and ignores the rest, and the terminal
  opens either way. OpenSSH accepts no names by default; many Linux distributions allow
  `AcceptEnv LANG LC_*`. Add the names you need to the server's `sshd_config`, or set them in the
  shell's startup files instead.
- Only the target host's shell gets them: not a jump host, not a Files tab, and not a port forward.
- A value read from a secret is masked in the terminal like a snippet's secret, so `env` or
  `echo $API_TOKEN` shows dots.

In the host form, **Environment variables** lists the variables the groups above pass down, greyed
with the group they come from. **Override** copies one onto this level to change it, and **Add
variable** adds a new one, as text or as a secret picked by name. The host details panel lists every
variable the host ends up with and where each one comes from.

## Agent forwarding

Agent forwarding lets a shell on the remote host use the keys in your local SSH agent: `git pull` from a
private repository, or `ssh` on to another server, without copying a key to the host.

```yaml
groups:
  - id: build
    name: Build servers
    ssh:
      forwardAgent: true
    hosts:
      - id: runner-1
        name: runner-1
        address: 10.0.4.2
      - id: vault
        name: vault
        address: 10.0.4.9
        ssh:
          forwardAgent: false
```

- It is off unless a host or a group above it turns it on, and it is inherited like the other `ssh`
  settings: **runner-1** above forwards, **vault** does not.
- It needs an SSH agent running on your machine (`SSH_AUTH_SOCK`, or Pageant on Windows). The host can
  still sign in with a key or a password; only the shell uses the agent.
- Only the terminal's shell on the target host gets it. A jump host never does, and neither do Files tabs,
  port forwards or the check that finds the host's OS.
- If the server refuses (`AllowAgentForwarding no`) or no agent is running, the terminal opens anyway,
  without forwarding.

<Aside type="caution" title="Forward the agent only to hosts you trust">
While you are connected, anyone with root on the remote host can use the keys in your agent, for example
to sign in to other servers as you. An agent that asks before each use (`ssh-add -c`) limits the damage.
</Aside>

In the host form, **Forward SSH agent** shows the inherited value with its group; turn on its override
switch to set it on this level. A warning shows while it is on. A terminal tab draws a key while the agent
is forwarded, and a faint key whose tooltip says why when it is not (the server refused it, or no local
agent runs); in a split tab each pane's header shows its own. The host details panel lists the setting
with its source, and its `ssh` command gains `-A`.

## Opening a terminal

Open the **Hosts** view from the activity bar (or **Show Hosts** in the palette). Groups and hosts
appear as written; the filter box matches name, address and tags, and tag chips narrow the list.
Double-click a host, or press <kbd>Enter</kbd>, to connect. The right-click menu has Connect, Edit,
Duplicate, Move to…, Delete and Copy address. A group can be deleted once it is empty.

The hosts you connected to lately show in a **Recent** strip above the list, newest first, with when
the last connect ended and whether it failed; its connect button opens the terminal again, and
**Clear** forgets the list. The sort menu's **Recently connected** orders each section the same way.
The list is kept on this machine per workspace and holds only the host, the time and the outcome,
never credentials. A deleted host drops out of it, and a renamed one shows by its new name.

From the keyboard:

- <kbd>⌘⇧H</kbd> / <kbd>Ctrl+Shift+H</kbd> runs **Connect to Host…**: a searchable list over name,
  address, group path and tags. The hosts you connected to lately come first, under **Recent**.
  <kbd>Enter</kbd> connects, or focuses the terminal if one for that host is already open.
- Quick-open (<kbd>⌘P</kbd>) lists hosts alongside operations and requests, recent ones first.
- The palette also has **Hosts: New Host…**, **Hosts: New Group…**, **Hosts: Edit Host…** and
  **Hosts: Import from SSH Config…**.

The terminal opens in an editor tab named after the host. It is a full terminal (colour, editors,
pagers, resize), and a host that is reached through a jump host is dialled hop by hop.

- Switching to another tab keeps the session alive; closing the tab ends it. Switching to another
  workspace or closing it ends every session.
- Terminal tabs are not restored when you restart Wirebench.
- When the remote shell exits, the tab stays and shows **Session ended (code N)** with **Reconnect**.
  If the connection could not be made, it shows **Could not connect** with **Reconnect**, and the
  reason is in the Problems tab.
- When the network drops the connection (Wi-Fi changes, a VPN drops, the laptop sleeps), the tab
  keeps its scrollback and reconnects on its own: it shows **Reconnecting… attempt N of 10** with a
  countdown, **Retry now** and **Cancel**, and tries at once when the machine wakes or the network
  comes back. A shell that exited, a sign-in failure or a changed host key never reconnects. After the
  last attempt the tab shows the reason with **Reconnect**. **Preferences → Terminal** turns this off
  and sets the number of attempts.
- Pasting text with more than one line asks first, with a preview, because a pasted script runs line
  by line. Both clipboard behaviours are in **Preferences → Terminal**: **Confirm multi-line paste**
  is on by default, and **Copy on select** is off by default.

## Local terminal

**Terminal: New Local Terminal** (<kbd>⌘⌥T</kbd> / <kbd>Ctrl+Alt+T</kbd>), or **New local terminal**
at the foot of the SSH sidebar, opens a tab with a shell on this machine, for the `git`, `curl` or
build you run next to the remote sessions. It sits with the SSH terminals and behaves like one: the
same colours, the multi-line paste prompt, copy on select and <kbd>⌘F</kbd> / <kbd>Ctrl+F</kbd> find.

- On macOS and Linux it runs your login shell (`$SHELL`), so it reads your profile. On Windows it runs
  PowerShell 7 when it is installed, otherwise Windows PowerShell. **Preferences → Terminal → Local
  shell** runs another program instead, such as `/bin/bash`, `cmd.exe` or `wsl.exe`.
- It starts in the workspace's folder when the workspace is shared from a folder of yours (a git clone
  or a synced folder), and in your home folder otherwise.
- When the shell exits, the tab shows **Shell ended (code N)** with **Restart**. Closing the tab, or
  switching to another workspace, ends the shell.
- A local terminal holds one shell: it does not split, join a layout or take broadcast input.
- `WIREBENCH_AREAS=local-terminal=off` removes it while keeping SSH; `ssh=off` removes both.

## Files

A **Files** tab browses a host's files beside this machine's and copies between them over SFTP. It
works through jump hosts exactly as the terminal does.

### Opening a Files tab

- **Open files** in a host's right-click menu, or **Files** in the host details panel.
- **Files** on a terminal tab's toolbar opens the files of the host in the focused pane. **Open
  terminal** on a Files tab's toolbar goes the other way. Each focuses the tab for that host if one is
  already open.
- **Open Files on Host…** in the palette, and the **Files** group in quick-open (<kbd>⌘P</kbd>).

The tab is named after the host with **· Files**. It has its own SSH connection, separate from any
terminal to the same host, so it signs in and checks the host key the same way (see
[Host keys](#host-keys)). Like a terminal, it keeps its folders and copies while you switch to
another tab, ends when you close it or switch workspace, and is not restored on restart.

### The two panes

This machine is on the left, starting in your home folder; the host is on the right, starting in the
folder you sign in to. Drag the line between them to resize. Each pane has:

- a **place picker** in its header: **This machine**, then every host by group and name. Switching a
  pane to another host connects to it, so both panes can be hosts and you copy from one host to
  another in the same tab;
- **Back**, **Up**, **Refresh** and a toggle for hidden files;
- a **path bar**: click a crumb to go there, or click the bar (<kbd>⌘L</kbd>, **Files: Go to
  Folder…**) to type a path. <kbd>Enter</kbd> goes there, `~` is the place's home, and
  <kbd>Escape</kbd> puts the crumbs back. A folder that can't be opened shows the reason under the bar,
  and the pane stays where it was.

The list has Name, Size, Modified and Permissions (as `rwxr-x---`) columns, folders first; click a
header to sort, again to reverse. Click, <kbd>⇧</kbd>-click and <kbd>⌘</kbd>-click select.
<kbd>Enter</kbd> opens a folder, <kbd>Backspace</kbd> goes up, <kbd>F2</kbd> renames in place,
<kbd>Delete</kbd> deletes after asking, <kbd>⌘A</kbd> selects everything, and <kbd>Tab</kbd> moves to
the other pane. The right-click menu has Open or Edit, Copy to other pane, Rename, Delete…,
Permissions…, New folder, Copy path and Refresh, and most are also **Files:** commands in the
palette.

A rename never replaces: a name that is already taken is refused, as is a new folder that exists.
Deleting a folder removes it with everything in it, and the confirmation says so.

### Copying and conflicts

- Drag a selection onto the other pane to copy it into the folder shown there, or onto a folder in
  the other pane to copy it into that folder. **Copy to other pane** does the same from the menu.
- Drop files from your file manager onto a host's pane to upload them there.
- Folders are copied with everything in them. A link to a file is followed; a link to a folder is not
  walked and shows as **Skipped**. Copying a folder into itself is refused before anything is written.

When a file being copied would land on a name that is already there, the copy stops and asks, showing
the size and modified time of both: **Skip**, **Keep both** (the copy becomes `name (1).ext`) or
**Replace**. Tick **Do this for the other clashes** to give the same answer to the rest of that copy;
otherwise each clash asks again. Closing the question is **Skip**. Nothing is replaced without
**Replace**.

Each file is written to `name.wirebench-part` beside the target and renamed into place when it is
complete, so a copy that fails leaves the old file as it was and no half-written file.

An upload keeps the local file's permission bits. A download gets your system's default permissions.

### Cancel and retry

While anything is being copied, the **Transfers** strip under the panes lists each file with its
direction, target folder, bytes done, speed and a bar. Three files copy at a time and the rest show
**Queued**. **Cancel** stops a file at once and removes its part file; it shows **Cancelled**. A file
that failed shows why, for example when the connection dropped. **Retry** on a failed or cancelled
file starts it again from the beginning: copies don't resume. **Clear done** removes the finished
rows, and the strip's header collapses it.

Closing a Files tab while files are still being copied asks first, then cancels them.

### Permissions

**Permissions…** on a host's file or folder opens read, write and execute boxes for owner, group and
others, next to an octal field (`644`) kept in step with them. **Apply** changes that one entry;
there is no recursive change, and changing the owner or group isn't supported. Permissions are
changed on hosts only, not on this machine.

### Editing a file

Double-click a file on a host, press <kbd>Enter</kbd> on it, or choose **Edit**, and it opens in
your system's default app for that kind of file. Each time you save it there, Wirebench uploads it.

- A banner over the panes lists the files open in an editor with each one's state: **Waiting for a
  save**, **Uploading…**, **Uploaded**, or why the upload failed. **Stop editing** stops uploading
  and deletes the local copy.
- If the file changed on the host since you opened it, the save is not uploaded and the banner asks:
  **Overwrite** uploads your version; **Keep remote** stops watching and leaves the host's version.
- A file over 50 MB asks first, because it is downloaded in full and each save uploads all of it.
- The copy lives in Wirebench's own data folder, readable only by you, and is deleted when the edit
  ends: on **Stop editing**, when you close the tab or the window, or when you switch workspace.
  Copies left behind by a crash are deleted on the next start.

### Access to this machine's files

The local pane can browse, copy into, rename and delete anything your user account can, anywhere on
the disk, like a file manager. Elsewhere, Wirebench only opens local files inside the open project
or ones you picked in a system dialog; the Files tab is the one deliberate exception, so the folders
you work with don't have to be granted one by one. The reasoning is in
[ADR-0025](https://github.com/wirebench/wirebench/blob/main/docs/adr/0025-the-sftp-local-pane-reads-and-writes-any-local-path.md).

That access belongs to the Files tab alone and goes when the SSH area is switched off (see
[Switching the area off](#switching-the-area-off)). A name that comes from a host is never trusted as
a path: a download whose name holds `/` or `\`, or is `.` or `..`, is refused, so a server can't write
outside the folder you chose.

### What Files doesn't do

- Resume an interrupted copy: **Retry** starts the file again.
- Change permissions recursively, change owner or group, or act as another user (`sudo`).
- Drag files out of a pane onto your file manager, or copy between two folders on this machine.
- Sync or compare folders, create links, or pack and unpack archives on the host.
- Fall back to SCP: a server without the SFTP subsystem is refused with `sftp-unavailable`.
- Copy files from the command line or the MCP server.

## Split terminals and layouts

A terminal tab can hold several terminals side by side, each its own session to the same host or another
one.

### Splitting

**Split right** (<kbd>⌘D</kbd> / <kbd>Ctrl+D</kbd>) and **Split down** (<kbd>⌘⇧D</kbd> /
<kbd>Ctrl+Shift+D</kbd>) are on the tab's toolbar and in each pane's menu. The new pane asks which host to
connect to, with the current pane's host chosen; <kbd>Enter</kbd> connects.

- A tab holds at most 12 panes, and a split is refused when either half would be narrower than 20 columns
  or shorter than 5 rows.
- Drag the line between two panes to resize them; double-click it to make them even.
- <kbd>⌘⌥</kbd> / <kbd>Ctrl+Alt</kbd> with an arrow key moves the focus to the neighbouring pane.
- **Close pane** in a pane's menu, or the close-tab shortcut while a pane has focus, ends that pane's
  session, and its neighbour takes the space. Closing the last pane closes the tab.
- Find, the paste check, reconnecting, **Files** and the host key prompt act on the focused pane.
- Once a tab is split, each pane has a slim header with its status, its host and its menu.

Connecting to a host focuses the tab you used last that has a pane on it, or opens a new tab. **Open in new
tab** (in the host's right-click menu and the palette) always opens another.

### Layouts

**Save layout…** on the tab's toolbar stores the tab's panes, their hosts and their sizes as a named
**layout**. A tab opened from a layout offers **Update "name"** or **Save as new…** instead.

The **Layouts** view in the SSH sidebar lists each layout with its hosts and pane count, and opens, renames
or deletes it. **Open Layout…** in the palette and the **Layouts** group in quick-open (<kbd>⌘P</kbd>) list
them too. Opening a layout opens one tab with the saved panes, all connecting at once, titled with the
layout's name. A pane whose host is no longer in `hosts.yaml` says so and offers **Remove pane**.

Layouts are kept on this machine only, per workspace, in Wirebench's own data folder. They name hosts by id
and hold nothing else: they are never written into the workspace, synced or shared with a team.

### Broadcast input

**Broadcast** on the toolbar of a tab with two or more panes (or **Terminal: Toggle Broadcast Input** in the
palette) sends what you type in one pane to the other panes of that tab. It starts with every pane ticked;
untick **Receive broadcast in …** in a pane's header to leave that pane out. Typing in a ticked pane reaches
every ticked pane; typing in an unticked pane reaches that pane only. Resizing, find and copying are never
broadcast.

Broadcast can't go unnoticed:

- a red banner across the tab says **Broadcasting to 2 of 3 panes** with **Stop**, adds **1 not connected**
  for a ticked pane that is not connected (it receives nothing), and **1 pane missed input** when a keystroke
  didn't reach a pane;
- every ticked pane has a red border, and the tab has a red dot;
- a paste into a ticked pane always asks first, single line or not, says how many panes will receive it,
  and ignores **Don't ask again**.

Broadcast is per tab, turns off when the tab closes or is down to one pane, and is never saved in a layout,
so it never comes back on by itself.

## Port forwarding

Forwarding rules let a host carry traffic for you: a database or a dashboard behind the host reached on a
port of this machine, a port on the host that reaches back to something on this machine, or a SOCKS proxy
that sends everything through the host.

### Rules in hosts.yaml

Groups and hosts take an optional `forwards` list beside `ssh`:

```yaml
groups:
  - id: prod
    name: Production
    ssh: { user: deploy, auth: { key: '${secret:prod_key}' } }
    forwards:
      - id: grafana
        type: local
        port: 3000
        target: localhost:3000
    hosts:
      - id: db-1
        name: db-1
        address: 10.0.1.7
        forwards:
          - id: pg
            type: local
            port: 5432
            target: localhost:5432
            autoStart: true
          - id: grafana
            enabled: false
hosts:
  - id: bastion
    name: bastion
    address: bastion.example.com
    ssh: { user: ops, auth: { agent: true } }
    forwards:
      - id: socks
        type: dynamic
        port: 1080
      - id: hook
        type: remote
        port: 8080
        target: localhost:3000
```

There are three types:

- **`local`** listens on this machine at `bind:port` and connects, through the host, to `target` as the host
  sees it. `db-1 · pg` above makes `127.0.0.1:5432` here reach the database on `db-1`.
- **`remote`** asks the host to listen at `bind:port` on its side and connects each arrival to `target` as
  this machine sees it.
- **`dynamic`** is a SOCKS5 proxy on this machine at `bind:port`; each connection's destination is reached
  through the host, and names are resolved on the host's side. It has no `target`.

The fields:

- `id` follows the host id rules and is unique within one list. `port` is 1–65535.
- `target` is `host:port` (`[v6]:port` for IPv6), required for `local` and `remote`.
- `bind` is `localhost`, an IPv4 or an IPv6 address; host names are refused. It defaults to `127.0.0.1` for
  `local` and `dynamic`, and to the host's own loopback for `remote`.
- `autoStart` (default `false`) starts the rule with the host's terminals.
- `enabled` (default `true`) switches a rule off.
- `forwards` holds no credentials and no `${…}` values.

### Inheritance and switching a rule off

A host gets every rule of the groups above it plus its own, merged by `id`. A nearer rule with the same id
replaces the farther one whole (fields are not merged), and `{ id, enabled: false }` switches an inherited
rule off: above, `db-1` has `pg` and not `grafana`, while every other host under **Production** has
`grafana`. A switch-off that names no rule above it is refused when the file is read, so a typo is caught.

You normally edit rules in the host and group dialogs, under **Port forwarding**: **Add rule** adds one at
that level, an inherited rule shows greyed with where it came from, **Override** copies it to this level to
edit it, and **Off** switches it off here. The rule form has the type, port, bind, target and **Start with
the host's terminals**.

### Starting and stopping

- **By hand:** **Start** on the rule, in the **Port forwarding** view of the SSH sidebar, in the host details
  panel, or **Start Port Forward…** in the palette. It runs until you stop it (**Stop**, **Stop Port
  Forward…**, **Stop All Port Forwards**).
- **With the terminals:** a rule with `autoStart` starts when a terminal to its host opens and stops when the
  host's last terminal closes. Starting it by hand while it runs this way keeps it running after the
  terminals close; stopping it by hand keeps it stopped until the host's next terminal.

Forwards use their own connection to the host, shared by that host's rules and separate from its
terminals, so a terminal closing or reconnecting never drops a forward. Switching workspace or closing the
window stops that window's forwards, and they are not restored on restart.

The **Port forwarding** view lists every rule of every host with its state, type (L, R or D),
`bind:port → target`, its host and where it came from, a filter box and **All**, **Running** and **Failed**
chips. Rules that are off show greyed with where they were switched off. A rule's menu has **Start on
another port…**, **Copy address**, **Edit rule** and **Stop**. If you edit a running rule, it keeps running
as it started and offers **Restart**.

While forwards run, the status bar shows **⇄ N**; it turns red when one has failed, and clicking it opens
the view.

### Ports and binds

- **Loopback by default.** Every listener binds `127.0.0.1` (a remote rule, the host's loopback) unless the
  rule says otherwise.
- **Network binds.** A rule with any other `bind` (for example `0.0.0.0`) is marked **network** everywhere it
  shows. Its first start on this machine asks first, because the port will be reachable from other machines.
  The answer is kept on this machine only, never in `hosts.yaml`, and changing the bind asks again.
- **Clashes.** A port that is already taken is refused, never moved: the error names the address and port,
  and the Wirebench rule holding it when it is one of yours. **Start on another port…** offers a free port
  and uses it for that run only.
- A `remote` rule the host refuses (the port is taken there, or the server doesn't allow forwarding) fails
  with the server's reason.

### Reconnecting

When the connection drops, the rules show **reconnecting** and Wirebench dials the host again on the same
schedule as a terminal (up to 10 attempts). Local and SOCKS listeners keep their ports meanwhile, so a client
pointed at them never reaches something else; connections arriving in the meantime are closed. A sign-in
failure or a changed host key isn't retried. After the last attempt the rules fail and the ports are freed.

### SOCKS has no password

The SOCKS proxy has no authentication: any program that can reach its address can use it while it runs. On
the default loopback bind that is any program on this machine. Only version 5 `CONNECT` is supported.

### From the command line

`wirebench ssh forward <host> [rule…]` opens the same rules from a terminal or a pipeline, in the foreground,
until you stop it. It reads the trusted host keys of the desktop app on this machine and never adds to them,
and a network bind needs `--allow-network-bind`. See the
[CLI reference](https://github.com/wirebench/wirebench/blob/main/docs/cli.md#wirebench-ssh-forward).

## Snippets

A snippet is a command, or a short script, that your team types again and again: restart a service, follow
a log, call a health check with a token. Keep it once in the workspace and run it in the terminal in front of
you, or on several hosts, a group or a tag at once. A run types the script into each terminal as if you had
typed it, so you see everything it does.

### The snippets file

Snippets live in `snippets.yaml`, beside `hosts.yaml`, and travel with the workspace the same way. A missing
file means no snippets. There is no per-machine store: keep personal snippets in a personal workspace.

```yaml
version: 1
packages:
  - id: deploy
    name: Deploy
    snippets:
      - id: restart-api
        name: Restart API
        tags: [deploy]
        script: sudo systemctl restart api
        confirm: true
      - id: tail-log
        name: Tail service log
        description: Follows a unit's journal
        tags: [logs]
        variables:
          - name: service
            default: api
          - name: lines
            label: Lines to show
            default: '200'
        script: journalctl -u ${service} -n ${lines} -f
snippets:
  - id: call-health
    name: Health with token
    script: |
      curl -s -H "Authorization: Bearer ${secret:api_token}" https://localhost/health
      echo
```

The rules:

- `version` is `1`, and keys Wirebench doesn't know are refused, as in `hosts.yaml`.
- Snippets sit in **packages**, one level deep, or at the top level (shown as **No package**). `id`s follow
  the host id rules and are unique across the whole file, packages and snippets together; `name` is free text.
- A snippet has a `script` and a `name`, and optionally a `description`, `tags`, `variables`, `enter`
  (default `true`) and `confirm` (default `false`).
- A file that doesn't parse is shown in the Snippets view and in the Problems tab (source **snippets**); the
  rest of the workspace still opens.

### The Snippets view

**Snippets** is in the SSH menu, under Hosts, with its count (**Show Snippets** in the palette). Packages are
sections you can fold, then **No package**. The filter box (<kbd>⌘F</kbd> / <kbd>Ctrl+F</kbd>) matches name,
description, script, tags and package, and tag chips narrow the list. Each row shows the first line of the
script and marks a snippet that has variables, uses a secret or always confirms.

- Hover a row for **Run** and **Insert** (Insert types the script without pressing <kbd>Enter</kbd>).
  Double-click runs it.
- Click a row to edit it in the right panel. The script editor marks declared variables, secrets and the
  `${…}` text left to the shell in three styles. **Insert secret…** adds `${secret:NAME}` from the known
  names, or stores a new value first. A run always types the _saved_ snippet, so **Run** with unsaved changes
  asks to save first.
- The row menu has Run…, Insert, Edit, Duplicate, Move to package…, Copy script and Delete. **New snippet**
  has **New package** beside it; a package can be renamed, and deleted once it is empty.

### Variables

A snippet declares its variables under `variables`, each with a `name` (letters, digits and `_`, not starting
with a digit, and not `secret`), an optional `label` for the form and an optional `default`. In the script,
`${service}` is replaced only when `service` is declared. Every other `${…}`, `$HOME` or `$(…)` reaches the
shell untouched, so shell variables keep working:

```sh
journalctl -u ${service} -n ${lines} -f   # declared: replaced by Wirebench
echo "$HOME ${PATH}"                      # not declared: left to the shell
```

When the script holds a `${name}` that isn't declared, the editor offers **Declare `${name}` as a variable**.

A run asks for the values, filled with the last values you used on this machine, else the defaults. Values
are inserted as written, without quoting: the script is responsible for its own quotes. A value can't hold a
line break or another control character, so a value can never type a second command.

### Secrets in snippets

`${secret:NAME}` in a script is resolved like a host's secret: from an external secret manager mapped to that
name, else from the value stored for this workspace on this machine. A missing value stops the run with
`secret-missing` and the name, before anything is typed.

- **Typed by the app.** The value is read and typed by Wirebench's main process. The interface, the run
  dialog's preview and every error only ever see the name, and the preview shows `••••`.
- **Masked on screen.** From the first run that uses it, the value is replaced with `••••` in everything that
  terminal shows, for the rest of the session: the echo of the command, a program printing it back, the
  scrollback, find, and what a reconnect replays.
- **Kept out of history, mostly.** A line holding a secret is typed with a leading space. bash with
  `HISTCONTROL=ignorespace` (or `ignoreboth`) and zsh with `HIST_IGNORE_SPACE` leave such lines out of their
  history; other shells, and those without the option, keep them. The run dialog says so.

Masking has limits:

- A very short value (a few characters) is masked everywhere it appears in that session, including in output
  that has nothing to do with the secret. Wirebench can't warn you, because the interface never learns the
  value's length.
- A shell that redraws a long line in pieces, moving the cursor inside the value, can show parts of it.
- A program that transforms the value (base64, hex, URL encoding) prints something that is not masked.

### Running a snippet

- **In the terminal in front:** a snippet without variables runs at once. A snippet with variables first
  shows a small form for them.
- **Run…** (the row menu, or **Run** while no terminal is in front) opens the run dialog: the variables, the
  open terminals to tick (the one you used last is ticked), **Add host, group or tag**, the script as it will
  be typed, and every protected host it reaches. The button says **Run on 3 hosts** when it reaches more
  than one.
- **Hosts, groups and tags.** A chip for a group or a tag shows the hosts it expands to when the run starts.
  A host with a connected terminal reuses the one you used last; the others get a new terminal tab, which
  connects with the usual host key prompt and sign-in and is typed into once the shell is quiet for a moment
  (at most 10 seconds after connecting).
- One message at the end says how it went, for example **Ran on 3 of 4 hosts · api-4: authentication
  failed**. A host that fails doesn't stop the others.
- The script you confirmed is the one typed: if another window or a pull changed the snippet meanwhile, the
  run is refused with `snippet-changed` and nothing is typed.

A multi-line script is sent as one block when the shell supports it (bracketed paste), so a line that waits
for input, such as a `sudo` password prompt, can't swallow the lines after it. Each terminal receives the
script once; to keep typing into several terminals, use [Broadcast input](#broadcast-input).

The values you used last and the hosts you picked last are remembered per snippet on this machine. Secret
values never are.

### Confirmation, protected hosts, Enter

A run asks first, in the run dialog, when it reaches two or more hosts, when it reaches a **protected** host,
or when the snippet has `confirm: true` (**Always confirm** in the editor). A run into one unprotected
terminal goes straight in.

Mark a group or a host protected with the **Protected** switch in the host dialog, or `protected: true` in
`hosts.yaml`. It is inherited like the `ssh` fields, so a nearer `protected: false` lifts a group's flag:

```yaml
groups:
  - id: prod
    name: Production
    protected: true
```

A protected host shows a shield in the Hosts view, and the run dialog names it with where the flag comes
from: **api-1 is protected (from Production)**.

`enter: false` (**Press Enter** off in the editor) types the script and leaves it at the prompt, so you read
it and press <kbd>Enter</kbd> yourself. **Insert** does the same for one run of any snippet.

### From the keyboard

- <kbd>⌘K</kbd> → **Run Snippet…** opens a list of snippets, matched on name, package, tags and first line.
  <kbd>Enter</kbd> runs the snippet into the terminal in front (through the run dialog when it must ask),
  or opens the run dialog when no terminal is in front.
- Quick-open (<kbd>⌘P</kbd>) lists snippets under **Snippets**, beside operations, requests and hosts.
- <kbd>⌘;</kbd> / <kbd>Ctrl+;</kbd> inside a terminal (**Terminal: Snippets…**) opens a picker over that
  terminal. <kbd>Enter</kbd> runs into it, <kbd>⌥Enter</kbd> / <kbd>Alt+Enter</kbd> inserts.
- The palette also has **Snippets: New Snippet…**, **Snippets: Edit Snippet…** and **Snippets: Run
  Snippet**.

### Suggestions while you type

When what you have typed on the command line is the start of a snippet's first line (three characters or
more, up to its first `${`), the rest of that line shows dimmed after the cursor, with the snippet's name and
**Tab**. <kbd>Tab</kbd> completes it without pressing <kbd>Enter</kbd>: a snippet with variables asks for them
first, a multi-line snippet is typed whole so you see all of it, and a protected host or `confirm: true` still
asks. Any other key carries on as usual, and <kbd>Tab</kbd> goes to the shell when no suggestion shows.

Wirebench follows only what you type, so a suggestion goes away and stays away until the next
<kbd>Enter</kbd> once you move the cursor, recall history, paste or press <kbd>Tab</kbd> yourself. None shows
in a full-screen program (an editor, a pager), in a disconnected terminal or while the pane broadcasts.
**Preferences → Terminal → Snippets → Suggest snippets** turns them off.

## Importing from an SSH config

If your hosts are already in an OpenSSH client config, bring them in rather than typing them again.
Run **Hosts: Import from SSH Config…** (or **Import…** in the Hosts view), then choose **Read
~/.ssh/config** or **Choose a file…**. Many SSH clients can write their hosts in this format.

Before anything is written, the dialog shows what the import will do: every host with its address,
user, port, jump host and authentication, the lines that will not come across, and notes. Choose
**Import** to add the hosts; **Cancel** leaves `hosts.yaml` as it was.

| In the SSH config                          | In `hosts.yaml`                                                                 |
| ------------------------------------------ | ------------------------------------------------------------------------------- |
| `Host web db` (each name without `*`, `?`) | one host per name; the id is the name in lower case with `-` for other symbols  |
| `HostName` (`%h` is the alias)             | the host's address; without one, the alias is the address                       |
| `Port`, `User`                             | port and user                                                                   |
| `ProxyJump a,b`, `ProxyCommand ssh -W %h:%p a` | the jump host; a hop that names no host in the file becomes a new host        |
| `IdentityFile`                             | the key you choose for it (below)                                               |
| `CertificateFile`                          | the key's certificate, stored as `NAME_cert` with the key (below)               |
| `ServerAliveInterval`, `ConnectTimeout`    | keep-alive and connect timeout                                                  |
| `SetEnv NAME=value …`                      | environment variables; the first value of a name wins                           |
| `ForwardAgent yes` / `no`                  | [agent forwarding](#agent-forwarding); a socket path or variable is not imported |
| `Host *` and lines before the first `Host` | settings on the new group, inherited by its hosts                               |

Each alias gets the settings `ssh` itself would use: the first value found for each option, in file
order, across the blocks whose patterns match. `Include` is followed one level deep.

**Keys.** For each key file the dialog asks what to do:

- **Use the SSH agent** (the default). Nothing is read; the host authenticates with the agent's keys.
- **Store as workspace secret.** When you click **Import**, Wirebench reads that one file and stores it
  as a workspace secret on this machine; the host gets `auth: { key: '${secret:NAME}' }`. An
  encrypted key also gets a `NAME_passphrase` reference; set its value in the host form.
- **Use an existing secret** that already holds the key.

A host with a `CertificateFile` shows the certificate on its key row. With a stored or existing secret
`NAME`, the certificate file is read on **Import** and stored as `NAME_cert` (a secret of that name that
already exists is kept), and the host gets `certificate: '${secret:NAME_cert}'`. With the agent it is
not read.

A key file is never opened unless you choose to store it, and its contents never reach the interface.

**Environment variables.** `SetEnv` values are written to `hosts.yaml` as they are, and the dialog
does not show them; a note says so. Replace any secret among them with `${secret:NAME}` after the
import. An entry that is not `NAME=value`, or that already holds `${secret:…}`, is skipped with a note.

**What is not imported.** `Match` blocks, other `ProxyCommand`s, an `Include` inside an included file,
and options such as `LocalForward` or `SendEnv` are listed by option name, file and line.
Their values are never shown, because a config can hold credentials in unexpected places. Options
with no meaning here (`IdentitiesOnly`, `StrictHostKeyChecking`, `UserKnownHostsFile` and a few
others) are counted. Known-hosts files are not read here; import their keys from the **Known hosts**
view (see [Importing known_hosts](#importing-known_hosts)).

**Existing hosts.** Every import adds one new group, named "SSH config" by default, and never changes
a host or group you already have. A host with the same address, port and user as an existing one is
skipped (you can import it anyway), and an id that is taken gets a suffix (`web-2`). Importing the
same file again adds only the hosts that are new.

## Session logs

A session log keeps what a terminal printed, so you can look back after the tab is closed: what a
migration reported, or what was run on a production host. Logging is off until you turn it on.

**Turning it on.** In a host's details, **Session logs** has a **Log sessions** switch. On a group,
right-click it and tick **Log sessions**: every host in the group, and in the groups inside it, is
logged unless a nearer group or the host itself says otherwise. The details show where a host's
setting comes from, and **Follow group** drops the host's own switch. The switches are kept on this
machine, never in `hosts.yaml`, so a shared workspace cannot turn logging on for someone else.

**What is written.** Only the output, as plain text: colours and other escape sequences are removed,
a line a progress bar rewrote is kept as it last looked, and what a full-screen program (an editor, a
pager, `top`) draws is replaced by one line saying it was not logged. What you type reaches a log only
as the host echoes it, so a password typed at a prompt that does not echo is never in one. Every
password, key and passphrase used to connect, and every secret a snippet typed, is masked as `••••`.
**Keep raw output** in Settings › Terminal also keeps the stream as the terminal received it, with
the same masking.

**Where logs live.** In Wirebench's data folder on this machine, under `session-logs/`, one folder per
workspace and host. Each log is a `.log` text file with a `.json` file beside it that records the
host, address, user, start, end and exit code. All logs together stay under **Session logs size
limit** (Settings › Terminal, 500 MB by default): past it the oldest logs are deleted first. A log a
session is still writing is never deleted.

**Reading them.** The host's details list its logs, newest first, with how the session ended and the
size. **Search logs** finds the logs that contain some text and shows the first line that matches;
open a log to read it, filtered to the lines that contain your text. Each log can also be revealed in
the file manager, or deleted.

Logs from a workspace shared through Wirebench Server stay on this machine too: nothing is uploaded.

## Host keys

Wirebench keeps the host keys it has trusted in `ssh-known-hosts.json` in its own data folder, per
machine, never in the workspace. A shared workspace therefore cannot pre-trust a key for you.

- **A host you haven't connected to before.** The connect stops and shows the key's fingerprint.
  Check it with the host's owner, then choose **Trust and connect**. Nothing is trusted without that
  click.
- **A host whose key has changed.** The connect is refused and the prompt shows the stored and the
  new fingerprint. The only way on is to tick **I understand the key changed** and choose
  **Replace key and connect**. A changed key can mean the machine was reinstalled, or that something
  is in the way; find out which before you replace it.

The **Known hosts** view lists the trusted keys; **Forget** one and the next connection asks again.

### Importing known_hosts

Hosts you already reach with `ssh` are usually in its `known_hosts` file. In the **Known hosts** view,
choose **Import known hosts…** (or run **Hosts: Import Known Hosts…**), then **Read ~/.ssh/known_hosts**
or **Choose a file…**. Nothing is written until you confirm the preview.

Only the hosts in `hosts.yaml` gain a key. Each host is looked up the way `ssh` does it: by its address
on port 22, or as `[address]:port` on any other port. A line matches through a comma list of names, a
pattern with `*` and `?` (a matching `!pattern` excludes the host), or a hashed name (`|1|…`, written
by `HashKnownHosts`), which is checked against each host's address.

The preview shows:

- **Keys to trust**: hosts with no trusted key of that type yet.
- **Different from a trusted key**: the stored and the file's fingerprint side by side. The stored
  key stays unless you tick **Replace**; replacing then asks you to tick **I understand these keys
  changed**, as a changed key does on connect.
- **Not imported**, by line: `@cert-authority` lines (they trust a signing key, not a host key),
  `@revoked` lines, lines that name no host in `hosts.yaml`, a second key of a type a host already
  got from an earlier line, and lines that are not a key Wirebench can read.

## Security notes

- A password, key or passphrase is read only in the main process, when you connect. It is handed to
  the SSH client and stays inside that client for the life of the session; Wirebench keeps no other
  copy, and nothing stores, sends to the interface or logs a value; a [session log](#session-logs)
  masks it. The interface only ever sees secret _names_.
- `hosts.yaml` cannot hold a literal secret, and the host form cannot write one.
- A window can only write to, resize or close sessions it opened itself, and acts only on its own
  Files sessions, copies, edits and forwards.
- Forwards listen on loopback unless a rule says otherwise, and a network bind needs a confirmation on
  each machine that the shared `hosts.yaml` cannot give. The SOCKS proxy has no authentication. No
  forwarded byte is logged.
- The Files tab's local pane reaches any file your account can; see
  [Access to this machine's files](#access-to-this-machines-files).
- Host keys are trusted on first use, by an explicit click, or imported from a known_hosts file you
  choose after reviewing them, and replaced only by a separate explicit confirmation.
- A snippet's secret is read and typed by the main process, only into a script saved in `snippets.yaml` and
  only into a terminal the same window opened; the interface never receives the value. Its output is masked
  as described in [Secrets in snippets](#secrets-in-snippets), with the limits listed there.

## Switching the area off

The SSH area is on by default in every edition. Operators and developers can switch it off with the
`WIREBENCH_AREAS` environment variable, a comma-separated list of `id=on|off`:

```sh
WIREBENCH_AREAS="ssh=off"
```

With `ssh=off`, the Hosts item disappears from the activity bar, its commands (including
**Connect to Host…**, the **Files:** and **Terminal:** commands and the port forwarding commands),
its quick-open entries, the Port forwarding, Layouts and Snippets views (with **Run Snippet…** and the snippet
suggestions) and the status bar item are gone, and the area's
channels are not registered in the main process, so nothing can reach it. Entries that aren't `<id>=on|off` are ignored.

The local terminal goes with the area. To keep SSH and remove only the local terminal (its command, its
sidebar entry and its channels), set `local-terminal=off`:

```sh
WIREBENCH_AREAS="local-terminal=off"
```

- audit entries for sessions,
