A workspace can describe the machines its APIs run on: servers, bastions, jump hosts. You write them
down once, in groups, and open an interactive SSH terminal to any of them from the **Hosts** view,
the command palette, or quick-open. The user, port, key and jump host are set on a group and
inherited by every host under it, and the credentials never leave Wirebench's main process.

<Aside type="note">
This part of the SSH area covers hosts, the terminal and files. See
[What is not here yet](#what-is-not-here-yet) for what comes later.
</Aside>

## The hosts file

Hosts live in `hosts.yaml`, beside `workspace.yaml` in the workspace folder, so they travel with the
workspace the same way the rest of it does (git, or the server). A missing file is an empty list of
hosts.

```yaml
version: 1
groups:
  - id: prod
    name: Production
    tags: [prod]
    ssh:
      user: deploy
      port: 22
      jump: bastion
      auth: { key: '${secret:prod_key}' }
    groups:
      - id: eu
        name: EU
        hosts:
          - id: api-1
            name: api-1
            address: 10.0.1.5
            ssh:
              auth: { password: '${secret:api1_pw}' }
hosts:
  - id: bastion
    name: bastion
    address: bastion.example.com
    tags: [jump]
    ssh:
      user: ops
      auth: { agent: true }
```

You normally don't edit the file by hand: the Hosts view reads and writes it. If you do, a problem in
the file is shown in the Hosts view and in the Problems tab (source **hosts**), and the rest of the
workspace still opens.

The rules:

- `version` is `1`. Keys Wirebench doesn't know are refused, as in `workspace.yaml`.
- `id` is stable and unique across the whole file, made of lowercase letters, digits and hyphens
  (`api-1`, `eu`). `name` is free text and can change; the id is what `jump` points at.
- `ssh` on a group or a host holds `user`, `port`, `jump`, `auth`, `keepAlive` and
  `connectTimeout` (both in seconds). Every field is optional at every level. A host must end up
  with a `user` and an `auth`, from itself or a group above it; otherwise connecting says which
  field is missing and where it can be set. The port defaults to 22, the keep-alive to 15 seconds
  and the connect timeout to 20 seconds.
- `tags` are plain strings. They feed the Hosts filter, the palette and quick-open, and carry no
  behaviour.
- `jump` names the id of another host. Chains are followed through that host's own `jump`; an
  unknown id or a loop is refused when the file is read.
- `auth` is exactly one of `{ password }`, `{ key, passphrase? }` or `{ agent: true }`. The agent
  option signs with your local SSH agent.

## Inheritance

Settings flow from the root of the tree down, one field at a time: a value set on a nearer level
wins. A host under **Production** and **EU** takes the user, port and jump host from **Production**
unless **EU** or the host sets its own.

`auth` counts as one field, not a merge of its parts. A host that sets `auth: { password: … }` drops
the group's key completely instead of adding a password to it.

In the host form, a field you haven't set shows the value it inherits, greyed, with where it came
from, for example `from prod` (or `default` for the built-in values). Turn on the override switch next to the field to edit the
field on that host; turn it off again to go back to inheriting. Changing a group's key changes every
host under it that doesn't override it.

## Secrets

Credentials are never written in `hosts.yaml`. `${secret:NAME}` is the only form accepted: a literal
password, key or passphrase is refused when the file is read or saved, so the file can be committed
and shared. `NAME` follows the same rules as everywhere else: letters, digits and underscores, not
starting with a digit. A `key` resolves to the private key _text_ (the secret holds the PEM), not to
a path, so the workspace works on every machine that holds the secret.

SSH secrets belong to the **workspace** on your machine, not to a project, because a host belongs to
the workspace. In the host form, the password, key and passphrase fields are pickers over the known
secret names, each marked with where it comes from. **Set value…** stores a value for a name on this
machine; the field is write-only and the value is never shown again or sent back to the interface.

When you connect, a name resolves like any other secret in the app: a name mapped to an
[external secret manager](/wirebench/docs/guides/secrets/#secrets-from-external-managers) comes from
its source, and any other name comes from the value stored for this workspace on this machine. A
missing value fails the connect with `secret-missing` and the name. Project secrets don't apply: a
secret you set on a project is not visible to a host.

## Opening a terminal

Open the **Hosts** view from the activity bar (or **Show Hosts** in the palette). Groups and hosts
appear as written; the filter box matches name, address and tags, and tag chips narrow the list.
Double-click a host, or press <kbd>Enter</kbd>, to connect. The right-click menu has Connect, Edit,
Duplicate, Move to…, Delete and Copy address. A group can be deleted once it is empty.

The hosts you connected to lately show in a **Recent** strip above the list, newest first, with when
the last connect ended and whether it failed; its connect button opens the terminal again, and
**Clear** forgets the list. The sort menu's **Recently connected** orders each section the same way.
The list is kept on this machine per workspace and holds only the host, the time and the outcome,
never credentials. A deleted host drops out of it, and a renamed one shows by its new name.

From the keyboard:

- <kbd>⌘⇧H</kbd> / <kbd>Ctrl+Shift+H</kbd> runs **Connect to Host…**: a searchable list over name,
  address, group path and tags. The hosts you connected to lately come first, under **Recent**.
  <kbd>Enter</kbd> connects, or focuses the terminal if one for that host is already open.
- Quick-open (<kbd>⌘P</kbd>) lists hosts alongside operations and requests, recent ones first.
- The palette also has **Hosts: New Host…**, **Hosts: New Group…**, **Hosts: Edit Host…** and
  **Hosts: Import from SSH Config…**.

The terminal opens in an editor tab named after the host. It is a full terminal (colour, editors,
pagers, resize), and a host that is reached through a jump host is dialled hop by hop.

- Switching to another tab keeps the session alive; closing the tab ends it. Switching to another
  workspace or closing it ends every session.
- Terminal tabs are not restored when you restart Wirebench.
- When the remote shell exits, the tab stays and shows **Session ended (code N)** with **Reconnect**.
  If the connection could not be made, it shows **Could not connect** with **Reconnect**, and the
  reason is in the Problems tab.
- When the network drops the connection (Wi-Fi changes, a VPN drops, the laptop sleeps), the tab
  keeps its scrollback and reconnects on its own: it shows **Reconnecting… attempt N of 10** with a
  countdown, **Retry now** and **Cancel**, and tries at once when the machine wakes or the network
  comes back. A shell that exited, a sign-in failure or a changed host key never reconnects. After the
  last attempt the tab shows the reason with **Reconnect**. **Preferences → Terminal** turns this off
  and sets the number of attempts.
- Pasting text with more than one line asks first, with a preview, because a pasted script runs line
  by line. Both clipboard behaviours are in **Preferences → Terminal**: **Confirm multi-line paste**
  is on by default, and **Copy on select** is off by default.

## Files

A **Files** tab browses a host's files beside this machine's and copies between them over SFTP. It
works through jump hosts exactly as the terminal does.

### Opening a Files tab

- **Open files** in a host's right-click menu, or **Files** in the host details panel.
- **Files** on a terminal tab's toolbar opens the files of the host in the focused pane. **Open
  terminal** on a Files tab's toolbar goes the other way. Each focuses the tab for that host if one is
  already open.
- **Open Files on Host…** in the palette, and the **Files** group in quick-open (<kbd>⌘P</kbd>).

The tab is named after the host with **· Files**. It has its own SSH connection, separate from any
terminal to the same host, so it signs in and checks the host key the same way (see
[Host keys](#host-keys)). Like a terminal, it keeps its folders and copies while you switch to
another tab, ends when you close it or switch workspace, and is not restored on restart.

### The two panes

This machine is on the left, starting in your home folder; the host is on the right, starting in the
folder you sign in to. Drag the line between them to resize. Each pane has:

- a **place picker** in its header: **This machine**, then every host by group and name. Switching a
  pane to another host connects to it, so both panes can be hosts and you copy from one host to
  another in the same tab;
- **Back**, **Up**, **Refresh** and a toggle for hidden files;
- a **path bar**: click a crumb to go there, or click the bar (<kbd>⌘L</kbd>, **Files: Go to
  Folder…**) to type a path. <kbd>Enter</kbd> goes there, `~` is the place's home, and
  <kbd>Escape</kbd> puts the crumbs back. A folder that can't be opened shows the reason under the bar,
  and the pane stays where it was.

The list has Name, Size, Modified and Permissions (as `rwxr-x---`) columns, folders first; click a
header to sort, again to reverse. Click, <kbd>⇧</kbd>-click and <kbd>⌘</kbd>-click select.
<kbd>Enter</kbd> opens a folder, <kbd>Backspace</kbd> goes up, <kbd>F2</kbd> renames in place,
<kbd>Delete</kbd> deletes after asking, <kbd>⌘A</kbd> selects everything, and <kbd>Tab</kbd> moves to
the other pane. The right-click menu has Open or Edit, Copy to other pane, Rename, Delete…,
Permissions…, New folder, Copy path and Refresh, and most are also **Files:** commands in the
palette.

A rename never replaces: a name that is already taken is refused, as is a new folder that exists.
Deleting a folder removes it with everything in it, and the confirmation says so.

### Copying and conflicts

- Drag a selection onto the other pane to copy it into the folder shown there, or onto a folder in
  the other pane to copy it into that folder. **Copy to other pane** does the same from the menu.
- Drop files from your file manager onto a host's pane to upload them there.
- Folders are copied with everything in them. A link to a file is followed; a link to a folder is not
  walked and shows as **Skipped**. Copying a folder into itself is refused before anything is written.

When a file being copied would land on a name that is already there, the copy stops and asks, showing
the size and modified time of both: **Skip**, **Keep both** (the copy becomes `name (1).ext`) or
**Replace**. Tick **Do this for the other clashes** to give the same answer to the rest of that copy;
otherwise each clash asks again. Closing the question is **Skip**. Nothing is replaced without
**Replace**.

Each file is written to `name.wirebench-part` beside the target and renamed into place when it is
complete, so a copy that fails leaves the old file as it was and no half-written file.

An upload keeps the local file's permission bits. A download gets your system's default permissions.

### Cancel and retry

While anything is being copied, the **Transfers** strip under the panes lists each file with its
direction, target folder, bytes done, speed and a bar. Three files copy at a time and the rest show
**Queued**. **Cancel** stops a file at once and removes its part file; it shows **Cancelled**. A file
that failed shows why, for example when the connection dropped. **Retry** on a failed or cancelled
file starts it again from the beginning: copies don't resume. **Clear done** removes the finished
rows, and the strip's header collapses it.

Closing a Files tab while files are still being copied asks first, then cancels them.

### Permissions

**Permissions…** on a host's file or folder opens read, write and execute boxes for owner, group and
others, next to an octal field (`644`) kept in step with them. **Apply** changes that one entry;
there is no recursive change, and changing the owner or group isn't supported. Permissions are
changed on hosts only, not on this machine.

### Editing a file

Double-click a file on a host, press <kbd>Enter</kbd> on it, or choose **Edit**, and it opens in
your system's default app for that kind of file. Each time you save it there, Wirebench uploads it.

- A banner over the panes lists the files open in an editor with each one's state: **Waiting for a
  save**, **Uploading…**, **Uploaded**, or why the upload failed. **Stop editing** stops uploading
  and deletes the local copy.
- If the file changed on the host since you opened it, the save is not uploaded and the banner asks:
  **Overwrite** uploads your version; **Keep remote** stops watching and leaves the host's version.
- A file over 50 MB asks first, because it is downloaded in full and each save uploads all of it.
- The copy lives in Wirebench's own data folder, readable only by you, and is deleted when the edit
  ends: on **Stop editing**, when you close the tab or the window, or when you switch workspace.
  Copies left behind by a crash are deleted on the next start.

### Access to this machine's files

The local pane can browse, copy into, rename and delete anything your user account can, anywhere on
the disk, like a file manager. Elsewhere, Wirebench only opens local files inside the open project
or ones you picked in a system dialog; the Files tab is the one deliberate exception, so the folders
you work with don't have to be granted one by one. The reasoning is in
[ADR-0025](https://github.com/wirebench/wirebench/blob/main/docs/adr/0025-the-sftp-local-pane-reads-and-writes-any-local-path.md).

That access belongs to the Files tab alone and goes when the SSH area is switched off (see
[Switching the area off](#switching-the-area-off)). A name that comes from a host is never trusted as
a path: a download whose name holds `/` or `\`, or is `.` or `..`, is refused, so a server can't write
outside the folder you chose.

### What Files doesn't do

- Resume an interrupted copy: **Retry** starts the file again.
- Change permissions recursively, change owner or group, or act as another user (`sudo`).
- Drag files out of a pane onto your file manager, or copy between two folders on this machine.
- Sync or compare folders, create links, or pack and unpack archives on the host.
- Fall back to SCP: a server without the SFTP subsystem is refused with `sftp-unavailable`.
- Copy files from the command line or the MCP server.

## Importing from an SSH config

If your hosts are already in an OpenSSH client config, bring them in rather than typing them again.
Run **Hosts: Import from SSH Config…** (or **Import…** in the Hosts view), then choose **Read
~/.ssh/config** or **Choose a file…**. Many SSH clients can write their hosts in this format.

Before anything is written, the dialog shows what the import will do: every host with its address,
user, port, jump host and authentication, the lines that will not come across, and notes. Choose
**Import** to add the hosts; **Cancel** leaves `hosts.yaml` as it was.

| In the SSH config                          | In `hosts.yaml`                                                                 |
| ------------------------------------------ | ------------------------------------------------------------------------------- |
| `Host web db` (each name without `*`, `?`) | one host per name; the id is the name in lower case with `-` for other symbols  |
| `HostName` (`%h` is the alias)             | the host's address; without one, the alias is the address                       |
| `Port`, `User`                             | port and user                                                                   |
| `ProxyJump a,b`, `ProxyCommand ssh -W %h:%p a` | the jump host; a hop that names no host in the file becomes a new host        |
| `IdentityFile`                             | the key you choose for it (below)                                               |
| `ServerAliveInterval`, `ConnectTimeout`    | keep-alive and connect timeout                                                  |
| `Host *` and lines before the first `Host` | settings on the new group, inherited by its hosts                               |

Each alias gets the settings `ssh` itself would use: the first value found for each option, in file
order, across the blocks whose patterns match. `Include` is followed one level deep.

**Keys.** For each key file the dialog asks what to do:

- **Use the SSH agent** (the default). Nothing is read; the host authenticates with the agent's keys.
- **Store as workspace secret.** When you click **Import**, Wirebench reads that one file and stores it
  as a workspace secret on this machine; the host gets `auth: { key: '${secret:NAME}' }`. An
  encrypted key also gets a `NAME_passphrase` reference; set its value in the host form.
- **Use an existing secret** that already holds the key.

A key file is never opened unless you choose to store it, and its contents never reach the interface.

**What is not imported.** `Match` blocks, other `ProxyCommand`s, an `Include` inside an included file,
and options such as `LocalForward`, `ForwardAgent` or `SendEnv` are listed by option name, file and line.
Their values are never shown, because a config can hold credentials in unexpected places. Options
with no meaning here (`IdentitiesOnly`, `StrictHostKeyChecking`, `UserKnownHostsFile` and a few
others) are counted. Known-hosts files are not imported: host keys are still trusted on first use.

**Existing hosts.** Every import adds one new group, named "SSH config" by default, and never changes
a host or group you already have. A host with the same address, port and user as an existing one is
skipped (you can import it anyway), and an id that is taken gets a suffix (`web-2`). Importing the
same file again adds only the hosts that are new.

## Session logs

A session log keeps what a terminal printed, so you can look back after the tab is closed: what a
migration reported, or what was run on a production host. Logging is off until you turn it on.

**Turning it on.** In a host's details, **Session logs** has a **Log sessions** switch. On a group,
right-click it and tick **Log sessions**: every host in the group, and in the groups inside it, is
logged unless a nearer group or the host itself says otherwise. The details show where a host's
setting comes from, and **Follow group** drops the host's own switch. The switches are kept on this
machine, never in `hosts.yaml`, so a shared workspace cannot turn logging on for someone else.

**What is written.** Only the output, as plain text: colours and other escape sequences are removed,
a line a progress bar rewrote is kept as it last looked, and what a full-screen program (an editor, a
pager, `top`) draws is replaced by one line saying it was not logged. What you type reaches a log only
as the host echoes it, so a password typed at a prompt that does not echo is never in one. Every
password, key and passphrase used to connect, and every secret a snippet typed, is masked as `••••`.
**Keep raw output** in Settings › Terminal also keeps the stream as the terminal received it, with
the same masking.

**Where logs live.** In Wirebench's data folder on this machine, under `session-logs/`, one folder per
workspace and host. Each log is a `.log` text file with a `.json` file beside it that records the
host, address, user, start, end and exit code. All logs together stay under **Session logs size
limit** (Settings › Terminal, 500 MB by default): past it the oldest logs are deleted first. A log a
session is still writing is never deleted.

**Reading them.** The host's details list its logs, newest first, with how the session ended and the
size. **Search logs** finds the logs that contain some text and shows the first line that matches;
open a log to read it, filtered to the lines that contain your text. Each log can also be revealed in
the file manager, or deleted.

Logs from a workspace shared through Wirebench Server stay on this machine too: nothing is uploaded.

## Host keys

Wirebench keeps the host keys it has trusted in `ssh-known-hosts.json` in its own data folder, per
machine, never in the workspace. A shared workspace therefore cannot pre-trust a key for you.

- **A host you haven't connected to before.** The connect stops and shows the key's fingerprint.
  Check it with the host's owner, then choose **Trust and connect**. Nothing is trusted without that
  click.
- **A host whose key has changed.** The connect is refused and the prompt shows the stored and the
  new fingerprint. The only way on is to tick **I understand the key changed** and choose
  **Replace key and connect**. A changed key can mean the machine was reinstalled, or that something
  is in the way; find out which before you replace it.

## Security notes

- A password, key or passphrase is read only in the main process, when you connect. It is handed to
  the SSH client and stays inside that client for the life of the session; Wirebench keeps no other
  copy, and nothing stores, sends to the interface or logs a value; a [session log](#session-logs)
  masks it. The interface only ever sees secret _names_.
- `hosts.yaml` cannot hold a literal secret, and the host form cannot write one.
- A window can only write to, resize or close sessions it opened itself, and acts only on its own
  Files sessions, copies and edits.
- The Files tab's local pane reaches any file your account can; see
  [Access to this machine's files](#access-to-this-machines-files).
- Host keys are trusted on first use, by an explicit click, and replaced only by a separate explicit
  confirmation.

## Switching the area off

The SSH area is on by default in every edition. Operators and developers can switch it off with the
`WIREBENCH_AREAS` environment variable, a comma-separated list of `id=on|off`:

```sh
WIREBENCH_AREAS="ssh=off"
```

With `ssh=off`, the Hosts item disappears from the activity bar, its commands (including
**Connect to Host…** and the **Files:** commands) and quick-open entries are gone, and the area's
channels are not registered in the main process, so nothing can reach it. Entries that aren't `<id>=on|off` are ignored.

## What is not here yet

This part does not include:

- snippets (saved commands run on one or many hosts),
- port forwarding and tunnels, or sending requests through a host,
- split or broadcast terminals,
- audit entries for sessions,
- a local terminal, SSH agent forwarding to the remote, or session recording with replay.
