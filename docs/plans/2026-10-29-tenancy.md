# Tenancy (slice 4 of #776) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for
> tracking.

**Goal:** Wirebench Server becomes multi-tenant. A `tenants` table, `tenant_id` on every table, forced row-level
security, tenant resolution by `Host`, per-tenant directories and data keys, the six guards of §5.4, the host-instance
lease and the self-hosted migration. A self-hosted installation stays one tenant, and nobody using it can tell.

**Architecture:** Five parts, one pull request each, in dependency order.

- **Part A** adds the roles, the tenants and the column:
  - an owner role and an app role, in tests and in production;
  - a frozen fixture at `0019`;
  - migration `0020`;
  - `src/tenancy/` (scope, tenant database, directory, job loop);
  - resolution by `Host`.
- **Part B** puts the first half of the modules in a tenant: identity, teams and licensing, sync with hooks and CI
  tokens, live updates and terminal shares.
- **Part C** puts the second half of the modules in a tenant, then forces row-level security:
  - scheduled runs, audit, SSO with session logs and the agent, the host module and the admin command line;
  - migration `0021` and the scope gate;
  - the two-tenant cases of every module and the isolation suite.
- **Part D** builds the per-tenant directories and data keys: the layout, the file step, the wrapped data key and the
  re-wrap.
- **Part E** builds the lease, the cap and the way back: `host_leases` in use, the instance cap, `admin tenancy
  revert`, the e2e on a migrated server, and the docs.

**Tech Stack:** TypeScript (ESM), Fastify 5, `pg`, PostgreSQL 16 (15 at least) row-level security, `node:crypto`
(HKDF, AES-256-GCM), vitest, Playwright.

**Spec:** `docs/specs/2026-10-24-wirebench-hosted-edition-design.md` §3.5, §4, §5.3–§5.5, §13, §14 and §19 (which wins
where they differ); ADR-0032 (as §19.15 amends it), ADR-0036; issue #ISSUE.

## Global Constraints

- **Invisible to self-hosted.**
  - No route, response, page, command output or file that a self-hosted user or operator sees names a tenant or a
    slug.
  - The only new operator surfaces are `admin tenancy check|status|role|revert`, the optional
    `WIREBENCH_SERVER_MIGRATION_DATABASE_URL`, and a start-up warning about a bypassing role.
  - Existing routes and channels keep their shapes, and every existing installation keeps upgrading with its current
    environment.
- **Hosted mode is test-only.** `loadConfig` refuses `WIREBENCH_SERVER_MODE=hosted` (spec §19.1). Tests build a hosted
  `ServerConfig` directly. Nothing of slices 5 to 8 is built: no signup, payment provider, wildcard name,
  `LISTEN`/`NOTIFY` or bypass role.
- **Row-level security is switched on last, and two-tenant tests come with it** (spec §19.13).
  - Parts A and B leave `tenant_id` with the default tenant's id as a constant default and no policy. An insert in a
    second tenant would get the default tenant's id, and every read would see every tenant's rows.
  - So until `0021`, Tasks 8 to 16 test on one tenant, and show that every statement of the moved module that a test
    exercises goes through `withTenant`. The module under test is registered with a `Proxy` over the one shared
    `ServerContext`. Its `db` getter throws `tenancy-unscoped`, and every other read and write passes through, so
    `ctx.license` and `ctx.log`, replaced during registration, still reach it. Modules not yet moved see the real
    `ctx`. The tenant database's test log asserts that each statement ran after `set_config`.
  - **The limit** (spec §19.13): with one tenant this shows a tenant, not the right one, and only on paths a test runs.
    The `defaultScope(` gate (Task 5) closes the commonest wrong-tenant case, and Tasks 18 and 19, in the same Part C
    pull request as `0021`, prove the rest under the policy.
  - Structures keyed by tenant get unit tests with two tenant ids.
  - Task 18 adds every module's two-tenant cases once Task 17's `0021` forces the policy.
  - A transitional policy in `0020` was the alternative. It was not taken: it would ship a policy whose `coalesce`
    lets an unscoped query see every row, and test a form that never runs in production.
- **No release is cut from main between the merges of Part A and Part E.** `admin tenancy revert` (Task 28) is the way
  back from `0020` and `0021`, and it lands with Part E.
- **Migrations** continue the global numbering: `0020` and `0021`, under `packages/server/migrations/tenancy/`. They
  are listed in `serve.ts`'s `allMigrations` beside the module folders. Every rebuilt key, index and foreign key keeps
  its `0019` name (spec §19.3, rule 6). New server env vars follow the config checklist in
  `packages/server/src/config.ts`. Slice 4 adds `WIREBENCH_SERVER_MIGRATION_DATABASE_URL`, and
  `WIREBENCH_SERVER_MODE`, which refuses `hosted`.
- **Sealed audit rows are never updated** (`0012`'s rule). The column is added with a constant default, which only
  changes the catalog.
- **The fixture is frozen.** Every migration test reads the checked-in `0019` fixture of Task 3, never a seed run
  through today's repositories.
- **Gates:**
  - Commit after every task with `WIREBENCH_SKIP_PERF=1 pnpm check` green, and run `pnpm test:perf` before each push.
  - Run `eslint .` with `NODE_OPTIONS=--max-old-space-size=8192` and the worktree ignore patterns.
  - Server integration tests need PostgreSQL (`packages/server/compose.yaml`), with the owner and app roles of Task 1.
- **House rules:**
  - No local Electron e2e windows; CI runs e2e.
  - Commit as Mohammed Naami, with no trailers.
  - Never name a product that inspired a feature.
  - Never let two implementers commit in one worktree at once.

## Review Focus

1. **A query that reaches another tenant.** A repository that still takes a raw `Querier`, a job that runs outside
   `forEachTenant`, a single-column foreign key between scoped tables, a unique index without `tenant_id`, or
   `workspaces.id` keyed alone. Tasks 4, 17, 18 and 19.
2. **A test that passes because the policy does not apply.** A superuser, `BYPASSRLS` or owner connection in the
   suites, a route template that `404`s for everyone, or a fill that wrote nothing. Tasks 1 and 19 (positive
   controls).
3. **The migration.** No sealed audit row rewritten, the `0019` names kept, a file step that resumes after a kill at
   every point, a re-wrap that never sets a cookie jar aside, and a revert that resumes and restores `0019` exactly.
   Tasks 4, 22, 24 and 28.
4. **Self-hosted unchanged.** `Host` never read in self-hosted mode, no slug in any output, an old compose volume and
   an old single URL both starting, and the browser e2e green on a migrated server. Tasks 2, 6 and 29.
5. **Pooled connections and the lease.** A client in doubt destroyed, a querier unusable after its unit, no two
   processes holding one user's checkout, a lost lease stopping its instance before expiry, and the cap evicting idle
   instances before it refuses. Tasks 5, 26 and 27.

## Part B — the modules in a tenant, first half

Every task in Parts B and C, up to Task 16, follows one recipe:

1. The module's repository functions take a `TenantQuerier` first, where they took a `Querier`.
2. Its routes call them with `ctx.tenancy.db(request.tenant)`.
3. Its timers go through `forEachTenant`.
4. Its in-memory keys lead with the tenant id.
5. Every read of `config.publicUrl`, and every value computed from it at registration, becomes a function of the
   request's scope through `tenantUrl` (spec §19.5).
6. Its tests stay on one tenant, with two checks on top:
   - **scoped:** the module under test is registered with `scopedContext(ctx)` (Task 5), whose `db` throws
     `tenancy-unscoped`, and the statement log shows every statement it ran inside a tenant transaction;
   - **keyed:** a unit test with two tenant ids for each in-memory structure it keys.

The two-tenant cases are written in Task 18, after `0021`, where they prove the policy rather than filters the
repositories never had.
